# M03-02 · VDP DMA: 68k transfer, fill, copy

**Milestone:** [M03 – VDP video](README.md)  
**Status:** Done  
**Depends on:** M03-01  
**Spec refs:** [05-vdp](../../docs/specs/05-vdp.md#dma)

## Story

As a **developer**, I want all three DMA types with 68k stall approximation and `onDma` events, so that graphics/palette uploads work and the ROM map can classify DMA sources.

## Scope

- 68k→VRAM/CRAM/VSRAM; source/length register update after transfer
- Fill and copy
- 68k freeze duration from bandwidth table
- `onDma` hook with source/dest/length

## Acceptance criteria

- [x] Sonic 1 title screen art arrives in VRAM via DMA — `gen_cli run` on Sonic 1 reports 891 68k→VDP DMAs (247,104 words) and 8 fills in the first 600 frames (palette, sprite table, H-scroll and art uploads), and the title screen renders correctly (M03-04)
- [x] Source address wrap at 128 KB boundary handled — unit test: a CRAM DMA from `$01FFFC` continues at `$000000`
- [x] Hook events match DMAs issued — unit tests check kind, target, source, destination and length of 68k, fill and copy DMAs; `gen_cli run` prints per-kind counts

## Test plan

- Unit tests; DMA test ROM

## Notes

- 68k→VDP DMA no longer runs instantly: the scheduler (`Machine::stepCpu`) freezes the 68k and gives the VDP time line by line (`Vdp::runDma`) at the bandwidth table (`DmaRates`, bytes per line: H40 18 active / 205 blank, H32 16 / 167; one word costs 2 bytes for every target). Data lands progressively, so a DMA spanning active lines is visible part-way.
- Registers 19-22 count down / up as the transfer runs; `onDma` fires when the DMA starts.
- Fill and copy still execute instantly, but the status DMA-busy bit stays set for their approximate duration (fill 1 byte per slot, copy 2) and while a fill waits for its data word.
- Not modeled: DMA/FIFO interaction, a separate CRAM/VSRAM rate, the DMA-from-RAM last-word quirk.
