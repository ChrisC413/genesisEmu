One clock to rule them all

Two CPUs, a video chip and two sound chips all run off one 53.69 MHz crystal. The scheduler keeps them in step, one scanline at a time, deterministically.

genesisEmu build notes4 min readStory M02-05

A Genesis is several chips working at once. The 68000 runs at one speed, the Z80 at another, the video chip draws pixels at a third, and the sound chips have rates of their own. All of these clocks are derived from a single crystal, the master clock (MCLK): 53.693175 MHz on NTSC consoles. The 68000 gets MCLK divided by 7, and the Z80 MCLK divided by 15.

An emulator runs one thing at a time, so it has to interleave the chips in a way that keeps them close enough together that no game can tell the difference. M02-05 built the scheduler that does this, in the Machine class that represents the whole console.

Everything is measured in master clocks

The scheduler keeps a 64-bit count of master clocks since power-on. A 64-bit counter at 53.7 MHz would take thousands of years to overflow, so the question never comes up. Every other quantity is expressed in master clocks as well. A scanline is 3,420 MCLK. An NTSC frame is 262 lines; a PAL frame is 313:

That makes an NTSC frame 896,040 MCLK, or about 59.92 frames per second, which was the first acceptance criterion and the first unit test.

A scanline at a time

Decision D-002 set the granularity: instruction-accurate CPUs and a scanline-based video chip. Each 68000 instruction runs to completion, adding its cycles × 7 to the CPU's clock. When the CPU's clock passes the end of the current line, the line ends:

Since instructions are atomic, the last one on a line generally finishes after the line boundary. The scheduler doesn't cut it short or discard the extra time. The CPU's clock simply stays ahead, and the next line accounts for it. Over a frame the totals come out exact, which the test checks: run(frames=1) stops at line 0 of the next frame at MCLK 896,040, with the overshoot carried forward.

Catching up

The other chips run lazily. Rather than interleaving the Z80 instruction by instruction with the 68000, the scheduler lets the 68000 run a whole line and then brings everything else up to the line's end with catchUp(). In M02 that function was an empty placeholder. M04 filled it with the Z80 and M05 with the sound chips. When the 68000 does something the Z80 must see at the exact moment, such as taking the Z80's bus, the bus calls a sync hook first so the Z80 catches up to the current time before the change. The structure was designed in from the start so those later stories didn't need to change the loop.

The same ROM, the same input and the same build always produce the same machine state, down to the last bit. Everything else in the project depends on that.

A run API for tools

Machine::run takes a limit: a number of frames, of instructions, of master clocks, or "until a breakpoint". It returns a RunResult saying why it stopped (limit reached, breakpoint, or a fault exception when stopOnFault is set) and how many instructions ran. step(cpu) runs exactly one instruction on either CPU, processing any line or frame boundary it crosses. This is the interface the CLI, the tests and later the debugger use. A breakpoint stops before its instruction and is resumable, using the hook behaviour from M01-01.

The machine also keeps a few cheap counters: exceptions per vector, fault count and the first fault's PC, V-ints per frame, and the PC that the last V-int interrupted. They aren't part of the emulated state, but the boot tests in M02-07 are built on them.

Deterministic by construction

Nothing in the loop depends on wall-clock time, thread scheduling or uninitialised memory. Given the same ROM and input, every run makes the same decisions in the same order. Decision D-011 requires it, and M02 backs it with a hash. Machine::stateHash() feeds every component's state, field by field, into an XXH3-64 hash. Values are serialised explicitly as little-endian bytes and never as raw struct memory, so compiler padding and host byte order can't leak in. A [determinism] unit test runs the synthetic boot ROM twice and requires identical hashes, and checks that the hash changes when the state does.

PAL's 313-line frames are implemented and unit-tested for line counts, but per decision D-020 (NTSC first) they're only lightly tested beyond that.
