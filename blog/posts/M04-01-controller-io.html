Eight buttons through six wires

A Genesis pad has more buttons than data lines. Games read it in phases by toggling one select line, and the six-button pad adds a secret handshake on top.

genesisEmu build notes4 min readStory M04-01

M02 gave genesisEmu controller ports that always reported "nothing pressed". M04's goal was to make the three games playable, and that starts with buttons. The Genesis controller connector has only six data lines for the pad to drive, plus one select line, TH, that the console drives. A 3-button pad has eight inputs (four directions, A, B, C and Start), so it multiplexes. A 6-button pad has twelve, and multiplexes more cleverly still.

The 3-button protocol

The game writes TH high or low through the port's data register, then reads the other bits back. The pad answers differently for each level. Buttons are active-low: 0 means pressed.

THbit 5bit 4bit 3bit 2bit 1bit 0
1CBRightLeftDownUp
0StartA00DownUp

The two forced zeros in the TH-low phase are how a game tells a pad from an empty port, whose pulled-up lines read all ones. Sonic 1 and 2 read the pad in exactly two phases, and the first unit test replays that sequence:

The 6-button handshake

The 6-button pad, released later, had to stay compatible with games that only know the 3-button protocol. It works by counting TH pulses. The first two cycles return normal 3-button data. On the third TH-low read, bits 0–3 all read 0, which a 3-button pad can never produce, and that identifies the pad. The fourth TH-high read returns the extra buttons: X, Y, Z and Mode. Then the cycle starts again.

If TH doesn't change for about 1.5 ms, the pad resets its counter. That's what keeps a game that reads once per frame in the "normal" phases. The emulator measures the timeout in master clocks, so it's deterministic:

The second unit test walks the whole sequence, checks the identification and extra-button phases, waits past the timeout and confirms the next read is phase 1 again rather than the identification pattern.

A pad reports buttons when the console asks, not when the player presses them. So the emulator samples the host's input once per frame, at a fixed point.

Input and determinism

Where host input enters the machine matters for determinism. If a key press reached the emulated pad at whatever moment the host's event arrived, two runs with "the same" input could diverge depending on timing. genesisEmu latches input once per frame, at the frame boundary. Machine::setInput only records the buttons for a port; the scheduler copies them into the I/O chip when the next frame starts:

A Genesis game samples its pad once per frame anyway, so players notice no difference. But a recording of "button X held from frame N to frame M" now reproduces a run exactly, and that's what the scripted-input tests in M04-03 are built on.

Each port has a pad type (3-button, 6-button or none), set from the config in the app or with --pad on the command line. A port with no pad reads as pulled-up inputs.

Verified with the games

The second criterion, that Sonic games detect a 3-button pad, was checked with scripted input. Sonic 1 and 2 start a game when Start is pressed, and Sonic runs and jumps on command. Sonic 3 & Knuckles navigates its data-select screen. All three runs are recorded as scripts in tests/scripts/ with hash checkpoints, so this behaviour is regression-tested from then on.
