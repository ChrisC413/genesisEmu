Which console am I running on?

Every Genesis game starts by asking the hardware about itself: region, video standard, and whether it has to unlock the video chip. The I/O registers answer.

genesisEmu build notes4 min readStory M02-02

Power on a Genesis and the first thing most games do is read a single byte at $A10001, the version register. It tells the software whether the console is Japanese or overseas, NTSC or PAL, and which hardware revision it is. Some games refuse to run on the wrong region. Others adjust their speed for 50 Hz PAL televisions. Sonic 1 checks it at boot. M02-02 implemented this register, the controller ports next to it, and TMSS, the lock-out mechanism added to later consoles.

One byte of identity

The version register packs its information into bits. Bit 7 means overseas (Americas or Europe), bit 6 means PAL timing, bit 5 is always set (no expansion unit attached), and the low bits hold the hardware version, with 0 meaning a console without TMSS:

The region comes from configuration if the user sets one, and otherwise from the cartridge header that M00-04 already parses. When a header lists several regions, the emulator prefers Americas, then Japan, then Europe. That follows decision D-020, NTSC first: the project is tuned for 60 Hz timing, and PAL is implemented but only lightly tested.

The unit test reads it back for each case: $A0 for an NTSC Americas console, $20 for Japan, $E0 for Europe (with the machine switching to 313-line PAL frames), and $A1 when TMSS is enabled. The region also decides the video timing, so a European setting changes more than one byte.

Controllers that aren't there yet

Next to the version register sit the data and control registers of the three controller ports. Input wasn't due until M04, but boot code initialises the ports and reads them, so they had to return sensible "nothing pressed" values.

The Genesis pad has more buttons than data lines, so it multiplexes. The console drives a select line, TH, and the pad answers with a different set of buttons for each level. With TH high you read Up, Down, Left, Right, B and C. With TH low you read Up, Down, A and Start, and two bits forced low, which is how a game recognises that a pad is connected. Buttons are active-low, so "released" reads as 1.

Rather than hard-coding idle values, M02-02 implemented the protocol properly with an all-released button mask. M04 only had to supply real buttons (and add the 6-button pad). The test checks the classic values: $7F with TH high, $33 with TH low, and $7F for the third port where nothing is connected.

Later consoles refuse to let a game touch the video chip until it writes the word SEGA to a register. That's TMSS.

TMSS: the 'SEGA' handshake

Later Genesis models include the Trademark Security System. Until software writes the four ASCII bytes 'SEGA' to $A14000, the video chip is locked. The idea was legal rather than technical: a game had to display Sega's trademark to run. Games handle it in their start-up code, typically writing the value only when the version register reports a non-zero hardware version.

genesisEmu models TMSS as an option, MachineConfig::tmss, which is off by default. When enabled, the bus checks the register on every VDP access, drops the access and records a VdpLocked issue until the magic value appears:

A unit test enables TMSS, checks that a VDP status read is refused and counted, writes $5345 and $4741 as two words, and checks that the VDP now answers. A second test runs the synthetic boot ROM with TMSS on and checks that it unlocks the VDP itself.

The real check: three regions, one game

The acceptance criterion was that Sonic 1's region check passes for its native region. The [rom] test went further: it boots Sonic 1 REV01 for 600 frames with each of the Japan, Americas and Europe version registers. All three reach the main loop without a single fault exception. That test needs the user's own ROM, so it runs locally with GENESIS_ROM_DIR set and reports skipped in CI.

The remaining I/O registers, such as serial ports and the memory-mode register at $A11000 (DRAM refresh for development cartridges), are stored or ignored as the spec describes. They do nothing useful on a retail console, but writing to them mustn't crash the emulator or trigger an unmapped-access report.
