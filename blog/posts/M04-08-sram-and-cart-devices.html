Battery saves and a socket for custom hardware

Sonic 3 & Knuckles saves your progress in battery-backed RAM on the cartridge. Supporting it meant building a small plug-in system for cartridge hardware, which the project's LED mod will plug into later.

genesisEmu build notes4 min readStory M04-08

A cartridge isn't always just ROM. Some carry extra hardware: battery-backed RAM for saves, bank-switching chips, or, in this project's future, a custom board that lights an LED for each Chaos Emerald collected (milestone M12). Sonic 3 & Knuckles has battery-backed save RAM (SRAM) for its save slots. M04-08 added it, and designed the mechanism so that other cartridge hardware can be added the same way.

A chain of devices

A cartridge is modelled as its ROM plus an ordered list of devices. Each device implements the ICartDevice interface and can do three things, all optional:

  • claim /TIME registers, the $A130xx range that the console strobes a dedicated cartridge pin for, where mappers and other cartridge hardware live;
  • overlay part of the cartridge address space, the way SRAM appears at $200000;
  • snoop writes to ROM space, which some hardware uses as a write-only port.

The first device that answers wins. Devices are part of the machine state: each one hashes its state into the determinism hash, and they'll be included in save states when those arrive in M06.

The bus integrates the chain through its page table from M02-01. A ROM page that a device overlays loses its direct fast-read pointer and becomes a Cart page, so every access there goes through the chain first. All other ROM pages keep the fast path, so a 4 MB game with a small SRAM region pays the cost on one 64 KB page only.

The SRAM controller is just the first cartridge device. The emerald-LED board planned for M12 will be another.

The SRAM controller

The first device is SramDevice, configured from the cartridge header's SRAM declaration, which M00-04 already parses. The header gives the address range and the byte lanes. Many cartridges wire an 8-bit SRAM chip to only the odd (or even) bytes of the 16-bit bus. Sonic 3 & Knuckles' SRAM sits at odd addresses from $200001, so only every other byte exists. $A130F1: ROM or RAM?

SRAM at $200000 overlaps ROM in a 4 MB image like S3K. The cartridge resolves this with a register at $A130F1: bit 0 maps SRAM in (hiding the ROM underneath), bit 1 write-protects it. The device claims that /TIME register:

If the ROM is small enough that SRAM doesn't overlap it, SRAM is mapped from power-on; otherwise the game has to switch it in. Before this story, S3K's save writes showed up in the bus issue log as ROM writes (M02-01). Now they land in SRAM.

Saving to disk

SRAM contents persist in <user data>/roms/<sha1>/<sha1>.srm, inside the per-ROM folder from M00-03. The app loads it when a ROM starts and writes it every 2 seconds while dirty, when the ROM changes and on exit. gen_cli run --sram file does the same for headless runs.

Tests

Unit tests cover SRAM over a 4 MB ROM switched by $A130F1 (ROM visible again when unmapped), SRAM beyond a small ROM mapped from power-on, persistence to a .srm file, and the chain itself: a test device claiming $A130E1 receives writes, and unclaimed $A130xx writes are logged as issues. The end-to-end check used scripted input. One run of S3K picks data-select slot 1, starts Angel Island and writes the .srm. A second run loads it and shows slot 1 as "ZONE 1" with lives instead of "NEW". The app logs "battery save loaded" for the same file. Saving from inside an interactive app session uses the same code but wasn't exercised directly, and the story notes that it still deserves a manual check.
