Sixteen megabytes, 256 pages

The 68000 can address 16 MB, and the Genesis wires that space to a cartridge, 64 KB of RAM, the sound CPU and the video chip. A table of 256 entries routes every access.

genesisEmu build notes4 min readStory M02-01

With M01 finished, genesisEmu had a CPU that executed instructions perfectly against a flat 16 MB block of test memory. A real Genesis isn't flat. Its 24-bit address space is split among very different things: the cartridge, 64 KB of work RAM, the Z80 sound processor's memory, I/O registers and the video chip. Some regions repeat (mirrors), some are empty, and some have side effects when read. M02-01 built the system bus that decides, for every access the CPU makes, what answers.

The map

A page table

Checking address ranges with a chain of ifs on every access would be slow, and the CPU makes millions of accesses per second. The major regions of the map all start and end on 64 KB boundaries, so the bus splits the address space into 256 pages of 64 KB and keeps a small table that says what each page is. Finer decoding, such as the individual registers inside the I/O page, happens only inside that page's handler:

A read is then a single switch on pages_[addr >> 16]. For ROM and RAM the bus also fills in the CPU's fast page pointers from M01, so the CPU reads that memory directly without calling the bus at all. That's safe because reading ROM or RAM has no side effects.

Building the table shows the whole map in a dozen lines. The RAM mirror is a nice detail: all 32 pages from $E00000 to $FFFFFF point at the same 64 KB array, so a write through one mirror is visible through all of them at no cost:

The machine pads the ROM image to a whole number of 64 KB pages, so every page of the cartridge gets a direct pointer. Pages past the end of the image are left unmapped.

Reading an address that nothing answers doesn't return zero. It returns whatever was last on the data bus.

Open bus

What does a read from an unmapped address return? On real hardware nothing drives the data lines, so the CPU sees whatever value they last held, usually part of the most recent instruction fetch. The issue log: who wrote there?

An access that hits nothing is usually a sign of a bug, either in the emulator or in the game. The bus records every such access with the address, value, size, direction and, most usefully, the PC of the instruction that made it. Four kinds are tracked: unmapped, a write to ROM, a Z80-area access while the 68000 doesn't own the Z80 bus, and a VDP access while TMSS hasn't unlocked it (see M02-02).

The story planned to log these through spdlog, but gen_core deliberately has no logging dependency (the core is a pure library). So the "log" is an in-memory list of the first 4,096 records plus a counter per kind, which gen_cli run prints. During M02 this caught something real. Sonic 3 & Knuckles writes to $200001 and above, which is its save-RAM range, and those writes showed up as ROM writes until save RAM was implemented in M04-08.

Byte lanes and odd details

The 68000 has a 16-bit data bus, and some devices behave differently for byte and word accesses. The bus handles each case explicitly, all from spec 04. A byte write to a VDP port puts the byte on both halves of the word. A word read from Z80 RAM returns the byte in both halves. A word write into the Z80 area delivers only its high byte. Each rule is a line or two in the dispatch functions, with a comment pointing at the spec.

Tests

tests/unit/bus_test.cpp covers every range in the spec's table. ROM is readable through fast pages and ignores writes. Space past the ROM, the expansion area and the 32X area return open bus and are logged. Work RAM is mirrored (a write at $E00000 is read back at $FF0000). The VDP ports are mirrored every 32 bytes. Unmapped writes are recorded with the PC of the writing instruction. A synthetic ROM provides the code, so none of these tests need a commercial game.
