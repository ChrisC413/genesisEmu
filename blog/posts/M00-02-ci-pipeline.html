Continuous integration on a zero-dollar budget

Every push is formatted, built twice and tested on GitHub's free Windows runners. Here is how it stays under three minutes.

genesisEmu build notes4 min readStory M00-02

An emulator is a large pile of small, exact rules, and it is easy to break one rule while fixing another. A tweak to the shifter can quietly break a flag in the arithmetic unit. Continuous integration is how this project notices. Every push and every pull request builds the whole project and runs every test.

There was one constraint. Decision D-016 says GitHub Actions free tier only: standard windows-latest runners, the standard cache and default artifact retention. No macOS runners, no larger machines, no paid minutes. The acceptance criteria even include a test for the constraint: the workflow files may contain no runs-on other than windows-latest.

The shape of the pipeline

The first job is deliberately cheap. It installs a pinned clang-format with pip, checks every source file, and runs tools/check_line_endings.py to reject carriage returns. If formatting fails, the build jobs never start, which keeps runner minutes free for builds that can pass. That behaviour was an acceptance criterion: run 40109907468 failed in clang-format and both build jobs show as skipped.

clang-format is pinned to version 22.1.8 and installed with pip rather than taken from whatever the runner image ships. Different versions of clang-format format the same code slightly differently. Pinning the version means "formatted on my machine" and "formatted in CI" mean the same thing. tools/format.py wraps it for local use.

Caching what is expensive

The slow part of a C++ build with vcpkg is building the dependencies: SDL3, ImGui, spdlog and the rest. They change rarely, so the workflow caches vcpkg's binary packages. The cache key combines the pinned vcpkg commit with a hash of the manifest:

A few details here came from things going wrong. The save step also runs after a failed configure, because by then vcpkg has usually finished compiling the libraries, and throwing that work away would make the next run slow too. The save is continue-on-error because the Debug and Release jobs run in parallel and may race to save the same key. vcpkg itself lives under RUNNER_TEMP, because actions/cache rejects paths containing ...

With a warm cache the two build jobs took 2m14s and 2m26s: about three minutes from push to green.

The acceptance criterion was a warm-cache build under ten minutes. Run 40117589455 recorded 2m14s for Debug and 2m26s for Release.

Test data that isn't in the repository

Later milestones added large external test suites: about a million 68000 test vectors and 1.6 million Z80 vectors from the SingleStepTests project, plus the AS macro assembler used for disassembly round trips. None of that is committed. tools/fetch-test-data.py downloads pinned versions listed in a lock file. The workflow caches each data set separately, keyed by the hash of that lock file, so one failed download can't poison the others.

What CI can't do

The free Windows runner has no GPU that can provide an OpenGL 3.3 context. The desktop app's smoke tests need one, so the app exits with code 77 when it can't create a context, and CTest maps 77 to skipped rather than failed. CI still compiles and links the app on every push; the smoke tests run on any developer machine with a GPU.

macOS isn't covered by CI at all. Instead, a local validation script prints a summary block that gets pasted into the pull request, and the PR template asks for it whenever platform code, CMake or the audio/video backends change. That template also carries a short checklist: CI green, acceptance criteria updated only when verified, and no ROMs, ROM-derived data or test data committed.

Proving the gate works

A CI pipeline that has never failed hasn't been tested, so the story asks for failures. Besides the formatting run above, run 40109963389 shows a deliberately failing CTest test (an app smoke test crash) failing the Test step and the job. Concurrency settings cancel an in-progress run when a newer commit lands on the same branch, and a Release build of main is packaged with cmake --install and uploaded as genesisEmu-windows-x64-<sha>.

At the end of M00 that pipeline ran 51 CTest tests on every push: 32 unit tests, 15 gen_cli tests, 3 app smoke tests and 1 [rom] test. By M05 the same workflow also checks millions of CPU vectors, golden video frames and audio hashes, still on the free tier.
