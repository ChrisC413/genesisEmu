Golden frames without golden images

How do you regression-test a renderer for commercial games without storing a single frame of them? Store hashes, keep the pictures on your own machine, and draw the differences in red.

genesisEmu build notes4 min readStory M03-11

The renderer built in M03 has a lot of rules, and a change to one can break another. A tweak to sprite masking could quietly break the HUD in Sonic 2's two-player mode. M03-11 added the safety net: golden frames. At fixed points in each game's start-up and attract sequence, the rendered frame must match a known-good result.

There's a constraint that shapes the whole design. The repository is public and can't contain anything from the games: no ROM bytes, and no screenshots either.

Hashes only

So the golden file stores hashes of frames, not the frames. Vdp::frameHash() runs XXH3-64 over the visible pixels and the frame's dimensions. The file lists, for each game (found by SHA-1), the frame number, the expected hash and a note of what the frame shows:

There are 19 checkpoints: 6 for Sonic 1, 7 for Sonic 2 and 6 for Sonic 3 & Knuckles. They were chosen to cover the features built in this milestone:

GameFramesWhat they exercise
Sonic 1150, 600, 1000, 1300, 2000, 2800SEGA logo, title screen, title card, Green Hill demo with parallax, water band and the loop
Sonic 2300, 500, 1100, 1400, 2000, 4600, 8000SEGA logo, intro, title, two-player Emerald Hill in interlace mode 2, Chemical Plant, Aquatic Ruin with the H-int water palette
Sonic 3 & Knuckles300, 800, 1400, 1700, 2200, 2600SEGA logo, title screen, Angel Island intro scenes and the attract demo

Every run starts from power-on with no input, and the emulator is deterministic, so frame 2,800 is always the same frame.

The repository proves the frame is right by its hash. The picture never leaves the developer's machine.

But a hash can't show you what broke

The weakness of hashes is that a mismatch tells you that something changed, not what. The fix is a local cache. Whenever a checkpoint matches, its raw pixels are saved outside the repository: in $GENESIS_GOLDEN_CACHE, or by default in a genesisEmu-golden-frames folder under the system's temp directory. The file name includes the frame number and the hash, so a stale picture can never stand in for the wrong golden value.

When a checkpoint later fails, three PNGs are written: the actual frame, the expected frame from the cache, and a diff image. The diff shows the actual frame dimmed to a quarter of its brightness, with every differing pixel in solid red:

The dimmed background keeps the frame recognisable, so you can see at a glance that, for example, the error is a band of wrong pixels along one sprite's edge. If there's no cached expected frame, perhaps on a fresh machine, only the actual PNG is written.

A PNG writer in ninety lines

The project had no image library, and adding one for this felt heavy. src/common/png.cpp is a minimal PNG encoder that writes uncompressed ("stored") deflate blocks. The files are larger than a real encoder would make, but they're valid PNGs that any viewer opens, and it reuses the CRC32 written in M00-04 for the chunk checksums.

Two ways to run it

The checks are available from the CLI and as a test:

  • gen_cli run --rom game.bin --check tests/golden/m03_frames.json --out dir runs to the last checkpoint, compares each hash, writes PNGs for mismatches into dir, and exits with code 3 if anything differs, the "check failure" code from M00-06.
  • The [rom] test tests/roms/frame_test.cpp does the same for every game found in GENESIS_ROM_DIR, writing diffs to a temp folder. Without ROMs, CTest reports it as skipped.

The mismatch path was checked deliberately: with a tampered golden file, gen_cli run --check wrote the _actual, _expected and _diff PNGs.

Changing a golden value

When emulation changes on purpose, say a more accurate sprite rule changes one frame, the golden hash has to change too. Spec 13 requires that to happen in its own commit, tagged [golden-update], with a reason. A changed hash is never buried in an unrelated change, and the history records each time the "correct" picture changed and why. When the Z80 started running in M04 and shifted attract-mode timing by a few frames, most of these hashes were updated that way, after the changed frames were compared with the cached ones: same scenes, small position shifts. M04 and M05 also added scripted-input checkpoints with frame, state and audio hashes, under the same rule.
