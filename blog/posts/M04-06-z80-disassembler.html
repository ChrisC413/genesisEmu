Reading the sound driver: a Z80 disassembler

The Z80 code in a Genesis cartridge is a small program that matters a lot for modding. Its disassembler shares its structure with the 68000's and passes the same reassembly test.

genesisEmu build notes3 min readStory M04-06

Every Sonic game ships a Z80 sound driver inside its ROM, copied into the Z80's RAM at boot (the 68000's side of that was M02-03). For the project's modding goals, that driver matters. A spliced special stage has to play its music through it, and understanding what the driver expects means reading its code. M04-06 built the Z80 disassembler, the counterpart of the 68000 one from M01-12.

One output structure for both CPUs

The Z80 disassembler doesn't define its own result type. It reuses the 68000 disassembler's Instruction, FlowType and SymbolResolver:

Tools built on top, such as the planned debugger views and code discovery for the ROM map, can handle both CPUs with one code path. An instruction has a mnemonic and operands, a length, a flow type, a static target when known, and the addresses it references. Some flow mappings are Z80-specific: a conditional RET is a conditional branch with no target, RST n is a call to its fixed vector, and HALT is a stop.

Syntax for the undocumented

The output targets The Macro Assembler AS with cpu z80undoc and relaxed on, the same assembler used for the 68000 code (D-010). Undocumented instructions need names, and AS has conventions for them: ixh and ixl for the halves of IX, sli for the undocumented shift, in f,(c) for the input that only sets flags, and the rlc (ix+$03),b form for the indexed bit operations that also copy the result into a register:

The second line is the same subtlety the CPU core had to handle (M04-05). With an index prefix, a plain register next to (IX+d) stays the real H or L, not the half of IX.

When an encoding has no text form that assembles back to the same bytes, the honest output is the bytes themselves.

When text can't round-trip

As with the 68000, some encodings can't be reproduced by an assembler. A DD prefix in front of an instruction that doesn't use HL changes nothing, so the assembler would never emit it. Several ED opcodes are mirrors of NEG, RETN or IM. ED 63 is a longer duplicate encoding of LD (nn),HL. Undefined ED opcodes do nothing. All of these become db lines with the raw bytes, and their flow is marked invalid:

The round trip

The acceptance criterion was the same as for the 68000: disassemble everything, reassemble with AS, compare bytes. gen_disasmz80_roundtrip builds a corpus of all 256 opcodes in each of the seven prefix groups (unprefixed, CB, ED, DD, FD, DDCB, FDCB), each with two sets of operand bytes. That's 3,584 items and 8,358 bytes. The listing goes through AS, and the result must match the corpus byte for byte. It does, and the test runs in CI as analysis.disasmz80_roundtrip, using the same pinned copy of AS as the 68000 test.

Relative jumps (JR, DJNZ) print their target address rather than the offset, the same convention as the 68000 branches, so the listing stays readable and AS computes the displacement.
