Keyboards, gamepads and "press a key"

The emulated pad needs a physical counterpart. M04-02 maps keyboards and SDL3 gamepads onto it, lets you rebind everything, and saves your choices in the config.

genesisEmu build notes4 min readStory M04-02

M04-01 taught the emulated console to read a pad. M04-02 is the other half: turning a keyboard or a modern gamepad into button presses on that pad, in a way the player can configure. It lives entirely in the app layer, in app::InputManager. The core only ever sees a 16-bit button mask per port.

Defaults that make sense

Spec 07 defines a default keymap, and common::defaultInputConfig() encodes it: arrow keys for the D-pad, A/S/D for the A, B and C buttons, Q/W/E for X/Y/Z, Return for Start and Right Shift for Mode. On a gamepad the Genesis's A-B-C row maps onto the west, south and east face buttons, a left-to-right row as on the original pad, and X/Y/Z use the shoulders and the top face button:

The left analogue stick doubles as the D-pad, with a threshold at about half deflection, because many modern controllers have a mushy D-pad and a good stick.

Hot-plug

SDL3 reports gamepads as they're connected and disconnected. The input manager opens each new gamepad and closes it on removal; the first gamepad drives port 1, the second port 2. Nothing has to be configured before plugging in.

Rebinding by capture

The Input panel (Emulation > Input...) lists every pad button for each port, the gamepad binding for each button, and every hotkey. Clicking a binding enters capture mode: the panel says "Press a key... (Esc cancels)", and the next key press (or gamepad button) becomes the new binding. Capture state is a tiny struct that remembers what's being rebound:

While capture is active, keys go to the capture and not to the game, so binding "A" to a pad button doesn't also press it. Likewise, when an ImGui text field has focus, keys reach neither the game nor the hotkeys.

Bindings are stored by name, like "Return" or "leftshoulder", so the config file stays readable and editable by hand.

Hotkeys for the future debugger

The same panel binds the emulator's own actions: pause (F5), step one frame (F6, while paused), fast-forward (hold Tab), step instruction (F11), step over (F10), and save or load state (Shift+F1–F4 and F1–F4). Pause, frame step and fast-forward worked straight away. The instruction-level and save-state actions belong to the debugger milestone, M06, so for now they log "not available yet". Defining the table early means the debugger only needs to add handlers, and users' custom bindings will already be in place.

Persisted, and forward-compatible

All of this goes into the JSON config from M00-03, in new input and view sections. Bindings are stored by name, which keeps the file readable and editable by hand. The view section holds the game-view settings from M03-10 (scale, aspect correction, filtering, overlay), which had been left unsaved there. Because hotkeys are read over the defaults, a new action added in a later version gets its default key even in an old config file:

A unit test, View settings and input bindings round-trip (M04-02), writes a config with non-default bindings and view settings, reads it back and compares.

What wasn't verified

The story is marked "Implemented; gamepad hot-plug needs a manual check", and both of its gaps are spelled out. No controller was attached to the build machine, so plugging and unplugging a gamepad while running, and the manual test with Xbox and PlayStation pads, were left for a person to do. The persistence criterion is checked by the unit test. Real-world input was exercised indirectly through the scripted tests of M04-03, which drive the same emulated pad.
