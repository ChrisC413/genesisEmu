The skeleton of a 68000

A register file, a bus interface and a 65,536-entry table of function pointers. Every instruction added later plugs into this structure.

genesisEmu build notes5 min readStory M01-01

The Sega Genesis has two processors. The main one, which runs the game logic, is a Motorola 68000 clocked at about 7.67 MHz. It's a 16/32-bit chip from 1979 with eight data registers, eight address registers and a reputation for being pleasant to program. Every Sonic game is mostly 68000 code, so the whole project depends on this core. The project's rules require it to be hand-written rather than borrowed from another emulator.

M01-01 doesn't execute any real instructions. It builds the structure that all twelve stories of the milestone fill in.

Machine state as a plain struct

Everything a program can observe about the CPU lives in one struct, State: eight data registers, eight address registers, the two stack pointers, the program counter, the status register, and two less obvious fields, ir and irc.

ir and irc model the 68000's prefetch queue. The real chip reads the next instruction words while it executes the current one, so at any moment it holds two words it has already fetched. That sounds like an implementation detail, but it's visible to software. Code that modifies the instruction right after the current one will find that the old version still runs. And when the CPU faults, the stacked state depends on what was in the queue. Modelling the queue explicitly is what later lets this core match the reference test suite bit for bit.

A plain struct also helps the later debugger milestones. Save states, register views and test harnesses can all read and write it directly.

The bus is an interface

The CPU doesn't know what's at any address. It talks to a Bus68k, an abstract class with read8, read16, write8, write16 and an interrupt acknowledge. The real Genesis memory map plugs in later (M02). In the tests it's a flat 16 MB array.

Two additions to the spec came from measurement. First, wait states, such as the extra time the 68000 loses when it touches the Z80's memory, are reported through a counter the bus increments, not a virtual call per instruction. Second, the bus can offer direct pages: 256 pointers, one per 64 KB of address space. If a page is plain memory with no side effects, like ROM or work RAM, the CPU reads it directly instead of making a virtual call. That made a measurable difference in the throughput benchmark (see M01-11).

One handler per opcode

A 68000 instruction starts with a 16-bit word, so there are exactly 65,536 possible first words. The core decodes them all up front into a table of function pointers:

Each family registers its opcodes with a mask-and-match helper: "every opcode where (op & 0xF100) == 0x7000 is MOVEQ". Handlers are C++ templates specialised on operand size and addressing mode, so MOVE.W (A0)+,D1 and MOVE.L -(A2),(A3) are separate, fully specialised functions with no mode dispatch left at run time. Executing an instruction is one array lookup and one indirect call.

The table is built once and shared. An acceptance criterion caps construction at 50 ms. The unit test asserts that in Release builds, and only checks under a second in Debug, where template-heavy code runs much slower.

Timing as a side effect of bus access

The design decision with the largest consequences was how to count cycles. Many emulators look cycle counts up in a per-instruction table. This core instead adds 4 cycles at the moment each word access happens, and adds internal delays explicitly with idle(n).

The story notes give the reason. When a word access hits an odd address, the 68000 aborts with an address error, and both the stacked information and the cycle count depend on how far the instruction had got. In the reference test suite, address errors make up 35–58% of the vectors in the word and long files. Charging time per access in the right order reproduces them exactly. A lookup table can't.

Hooks that cost nothing when unused

genesisEmu is a reverse-engineering tool, so the CPU must be observable. core/hooks.hpp defines a Hooks struct of plain function pointers plus a context pointer, deliberately not std::function or virtual calls. When a pointer is null, the cost is one well-predicted branch.

  • onInstr fires before each instruction and can return Action::Break. The debugger's breakpoints will use this.
  • onAccess fires for every memory access with its kind (fetch, read, write), address, size, value and the PC of the instruction responsible. Coverage maps and watchpoints will use this.
  • onIrq reports accepted interrupts.

A unit test runs MOVE.L D0,(A0)+ and checks that it reports exactly three accesses, two word writes and one prefetch, each tagged with the instruction's own PC. A second step with onInstr returning Break must execute nothing and return 0 cycles. Stepping again runs the instruction without asking the hook a second time, which the debugger needs to resume from a breakpoint.

Illegal from day one

The last criterion was that an unimplemented opcode raises the illegal-instruction exception. It isn't stubbed. The unit test checks vector 4 for ILLEGAL, 10 for line A and 11 for line F, that the stacked PC points at the offending opcode, and the 34-cycle cost. Every later story only has to replace table entries. Anything still missing fails safely and visibly.
