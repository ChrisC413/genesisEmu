Talking to the video chip, exactly

The VDP's command port has latch rules that look like trivia until a game depends on one. M03-01 implemented all of them and gave each one a unit test.

genesisEmu build notes5 min readStory M03-01

M02 gave genesisEmu a VDP that accepted commands well enough to boot three games. M03 was the video milestone, and before drawing a single pixel it made the chip's interface exact. Rendering reads VRAM, CRAM and VSRAM, so if a byte lands one address off, or a write that should be dropped isn't, every later rendering story inherits the error.

Three memories behind two ports

The VDP owns three memories the 68000 can't address directly:

  • VRAM, 64 KB: tile graphics, the name tables that arrange tiles into planes, the sprite table and the horizontal scroll table;
  • CRAM, 64 words: the palette, four lines of 16 colours, each a 9-bit 0000 BBB0 GGG0 RRR0 value;
  • VSRAM, 40 words: vertical scroll values.

All access goes through the data port, after a two-word command on the control port has set a 16-bit address and a 6-bit code that says which memory, read or write, and whether to start DMA. The state the VDP keeps for this is small: the address, the code, a pending flag between the first and second command word, a read buffer, and the 24 registers.

The latch rules

The interesting part is how the control port interprets words. M03-01 implemented the rules the hardware actually follows, which aren't all in the official documentation:

  • A first command word sets address bits A13–A0 and code bits CD1–CD0 and arms pending. The second sets A15–A14 and CD5–CD2.
  • A lone first word, one that is never followed by a second, keeps A15–A14 from the most recent second word.
  • A register write also loads A13–A0 and CD1–CD0 from its bits. That leaves CD1–CD0 = 2, which isn't a valid target, so stray data writes after a register write are dropped, as on hardware.
  • Any data-port access or status read clears pending.

A register write quietly changes the access target too. Data written after it goes nowhere, on hardware and in the emulator.

Reads, writes and wraparound

Each memory has its own write behaviour, and writeTarget shows them side by side. A VRAM write to an odd address swaps the bytes of the word. CRAM keeps only the nine colour bits and wraps every 64 words. VSRAM has 40 entries inside a 64-word address window, so writes to entries 40–63 are dropped:

Reads go through a read buffer. CRAM and VSRAM are narrower than 16 bits, and the unused bits of a read come from whatever the buffer last held. There's also an undocumented read code, $0C, an 8-bit VRAM read that puts one byte in the low half of the word. It's implemented and tested like the documented codes.

A FIFO, approximately

On hardware, data-port writes go into a four-entry FIFO, and during active display the VDP only drains it at certain moments. Writing faster than that stalls the 68000. genesisEmu models the FIFO only as far as the status register shows it: writes during active display fill it, it drains at the end of each line, and the "FIFO empty" and "FIFO full" bits follow. Writes never stall the CPU. The story records this as an approximation; none of the target games needed more.

The sprite cache

One hardware detail affects rendering directly. The VDP keeps a private copy of the first four bytes (Y position, size and link) of every entry in the sprite attribute table. That copy is updated only when the 68000 writes VRAM inside the table. If a game moves the table to another address, the cache isn't reloaded, and the sprite renderer (M03-07) keeps using the old values.

Tested edge by edge

tests/unit/vdp_test.cpp has a case for each rule: the read and write codes for every memory, the 8-bit VRAM read, invalid codes being dropped, pending cleared by a data or status access, the A15–A14 latch reused by a lone first word, register writes reloading the code, CRAM and VSRAM wrapping, the status bits, and the sprite cache following only writes inside the table. The DMA bit in a command is ignored while DMA is disabled in register 1, which M03-02 builds on.

The story is explicit about what isn't modelled: Master System compatibility mode, the HV-counter latch bit and the 128 KB VRAM mode. None of the target games use them, and the story doesn't claim otherwise. It also notes that no free VDP test ROM was run, because the project's fetch script doesn't download any.
