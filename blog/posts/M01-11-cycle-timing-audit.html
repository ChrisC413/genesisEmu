Counting every cycle, then counting how fast

996,322 vectors, zero cycle mismatches, two documented exclusions, and a throughput benchmark that came in just short of its target.

genesisEmu build notes4 min readStory M01-11

Why does an emulator care how many clock cycles an instruction takes? On the Genesis, timing is behaviour. The video chip raises its interrupts at fixed points in the frame, DMA transfers steal time from the CPU, and the sound CPU runs alongside on its own clock. A game that does slightly too much work per frame on real hardware drops a frame. An emulator that runs the same code a little too fast won't. A Sonic water level changes its palette at a precise scanline, and if the CPU reaches that code a few dozen cycles late, the water line moves.

Decision D-002 sets the project's level of accuracy. Instructions execute atomically, but each must take exactly the right number of cycles. M01-11 was the audit that checked it across the whole instruction set.

The result

996,322 of 996,322 non-excluded vectors pass, including exact cycle counts.

Every earlier story had already required exact cycles for its own instruction families. The audit ran the full suite (1,000,060 vectors in 124 files, pinned to commit e0d5ece9) and accounted for every vector that didn't pass. There are exactly two kinds, and both are listed in tests/m68k/sst_exclusions.txt and in the story:

VectorsWhy they're excluded
3,736 in ASR.b/w/lRegister count greater than the operand size on a negative operand. The suite expects C = X = 0; a bit-by-bit shift keeps shifting out the sign bit, so the manual ("set according to the last bit shifted out") and Musashi give 1. The core follows the manual.
2 in ASL.bThe expected final D2 differs in all 32 bits, which a byte shift can't do. The vectors are corrupt.

Neither exclusion is about timing. In cycle terms the core matches the reference everywhere.

Why per-access timing paid off

Looking back, the decision that made this possible was M01-01's: charge 4 cycles per word access when the access happens, plus explicit internal delays, instead of looking up a total per instruction. A table can give the right total for an instruction that completes. It can't give the right total for one that faults halfway through, which is a large share of the word and long vectors. With per-access timing, the cycle count at the fault is simply whatever had been charged so far, plus the 50 cycles of the address-error sequence.

The approach also makes deviations visible. Where the suite and common timing tables disagree, the story notes record the suite's value and the core follows it: ADDQ.L/SUBQ.L #,An takes 6 cycles rather than 8, BTST with an immediate bit number on a register takes 10, and the DIVS overflow path takes (8 or 9) × 2.

The benchmark: honest about a near miss

The second criterion was speed: at least 100 million 68000 instructions per second on the reference machine. A real 68000 at 7.67 MHz manages roughly 1.3 million instructions per second at most, so 100 MIPS sounds excessive. The headroom is deliberate. Later milestones add instrumentation on every access, coverage maps, fast-forward and analysis passes that replay long stretches of execution, and all of that needs a core with a lot of spare speed.

gen_m68k_bench runs a mix modelled on typical Sonic-style code: block copies, table lookups, arithmetic, branches and subroutine calls. It reports instructions per second. A --virtual flag turns off the direct memory pages so the two bus paths can be compared:

The fast pages were added during this audit. When the bus marks a 64 KB page as plain memory, the CPU's readWord reads two bytes from a pointer instead of making a virtual call. Hooks still see every access, so instrumentation loses nothing.

The measured result, Release build with MSVC on an i7-11700KF: 98–100 MIPS with the fast pages, and 93 MIPS through the virtual bus calls. That's about 110 times a real 68000. It's also not quite the target, and the class of machine the architecture spec budgets for (an Apple M1 or a Ryzen 5 3600) is probably a little slower. So the box stays unchecked and the story stays "In progress", with a note that it hasn't been profiled further.

Exactness in practice

The payoff came in later milestones. M02's boot tests record a deterministic state hash after N frames, and those hashes only stay stable if timing is exact. When M03 introduced DMA, which freezes the 68000 while the video chip copies memory, the boot hashes changed in a deliberate, reviewed [golden-update] commit, because CPU timing had legitimately changed. Timing is visible enough to be tested, which is what the audit was for.
