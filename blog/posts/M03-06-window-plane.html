The window: a plane that doesn't scroll

Status bars and split screens need a part of the picture that stays put while the rest scrolls. The VDP's window plane does this by replacing plane A in a rectangle of the screen.

genesisEmu build notes4 min readStory M03-06

Planes A and B scroll. That's their job. But many games want part of the screen not to scroll: a status bar, a menu panel, a text box. Sprites could do it, but they're limited per line, and a full-width bar would use up most of them. So the VDP has a third tile layer, the window. In a region of the screen it replaces plane A, it ignores both scroll registers, and it reads from its own name table.

M03-06 is the shortest of the rendering stories, but it shows well how the renderer fits together.

Where the window is

Two registers define the region. Register 17 gives a horizontal boundary in units of 16 pixels and a direction bit (window left or right of it). Register 18 gives a vertical boundary in units of 8 lines and a direction bit (window above or below). The rule for combining them follows the hardware: if a line falls in the vertical window region, the whole line is window; otherwise the horizontal range applies.

Typical uses: a status bar at the top or bottom (vertical boundary), a side panel (horizontal boundary), or no window at all (both boundaries at zero with the direction bits clear).

Drawing it

The window's renderer is a simplified copy of the plane renderer: no horizontal scroll, no vertical scroll, a fixed name-table width (64 cells in the 320-pixel mode, 32 in the 256-pixel mode) and its own name-table base from register 3. It writes into the same line buffer as plane A, over the window's columns. From the composer's point of view the window simply is plane A there, with its own priority bits, so priorities and shadow/highlight (M03-08) apply to it automatically.

The renderer only draws plane A at all when part of the line is outside the window. On a line that's entirely window, it skips the scrolled plane-A fetch.

To the composer, the window simply is plane A in its region. Every other rule applies to it for free.

Layer toggles

That excerpt also shows the LayerMask, a set of debug switches that hide plane B, plane A, the window or sprites, or keep only high- or low-priority pixels. They aren't part of the emulated state and don't affect the state hash. They're tools for the reverse engineer: hide plane A and you can see what's behind the foreground; show only high-priority pixels and you can see what the game draws in front of sprites.

What's not modelled

Real hardware has a known bug at the boundary between the window and plane A: when plane A is fine-scrolled horizontally, the first column after the window can be garbled. The story notes that this isn't modelled. A game that relied on it would render that column cleanly in genesisEmu.

Verified with synthetic VRAM

The acceptance criterion asked for a test ROM. The project uses a synthetic unit test instead, which needs no external file and is easier to reason about. It builds a plane A pattern and a different window pattern in VRAM, then checks the window to the left and to the right of a horizontal boundary, above and below a vertical one, that scrolling plane A doesn't move the window, and that the debug toggle hides it.

The game-level check, Sonic 2's two-player mode and menus look right, is still open. Reaching those screens needs menu navigation, which needs controller input from M04, so the story stays "In progress" and says why.
