Parallax: scrolling every line differently

Sonic's backgrounds move at several speeds at once: clouds slowly, mountains faster, the ground at full speed. The VDP lets each scanline scroll on its own, and so does genesisEmu.

genesisEmu build notes4 min readStory M03-05

Green Hill Zone's background is one of the most recognisable images of 16-bit gaming. Clouds drift slowly, mountains slide past faster, the lake shimmers, and the foreground moves at full speed. It's all one background plane. The trick is that the Genesis can scroll every line of a plane by a different amount. M03-05 implemented the VDP's scrolling modes, horizontal and vertical.

Horizontal scroll: a table in VRAM

Horizontal scroll values live in a table in VRAM (its address is in register 13). Each entry holds two words, one for plane A and one for plane B. Register 11 picks how many entries the table has:

  • full screen: one entry for the whole frame;
  • per cell: one entry per 8-line strip;
  • per line: one entry for every scanline, which is what parallax needs;
  • a prohibited fourth setting, which on hardware repeats the first eight entries. The emulator does the same rather than guessing.

The scroll value is 10 bits. The renderer subtracts it from the screen X position and wraps by the plane width, so a plane scrolls around seamlessly. With per-line scrolling, a game writes a different value for each band of the background every frame. A slow-moving cloud band gets a small offset, the ground a large one, and the eye reads it as depth.

Vertical scroll: per screen or per column

Vertical scroll values live in VSRAM. Register 11 chooses between one value for the whole plane and one value per 2-cell column, a 16-pixel-wide strip. Column scrolling allows effects such as rippling or wobbling backgrounds, and it's the reason VSRAM has 40 entries: 20 columns × 2 planes.

Combining horizontal and column scrolling raises a question: which column does a pixel belong to after the plane has been scrolled sideways? genesisEmu follows the hardware's fetch grid, which moves with the fine horizontal scroll. That leaves a partly visible column at the left edge that has no VSRAM entry of its own. What real hardware shows there is a known quirk, and the emulator approximates it, as the code comment explains:

Vertical scroll values are 10 bits normally and 11 in interlace mode 2 (M03-09), where the plane is twice as tall in pixels.

Green Hill Zone's background is one plane. The depth comes from scrolling each band of lines by a different amount.

Recording what happened

As each line is rendered, the renderer records the scroll values it used, horizontal for both planes and vertical for the first column, into a per-line array exposed as Vdp::lineInfo(). Nothing in emulation needs it. It's there for the debugger's VDP viewers planned for M06, which can then show exactly how a frame was scrolled without re-deriving it from VRAM.

Verified, and not verified

Unit tests build planes with recognisable patterns and check each mode: full, per-cell and per-line horizontal scroll, and full-screen and per-column vertical scroll. The visual check was Sonic 1's Green Hill Zone attract demo at frames 1,300, 2,000 and 2,800. The clouds, mountains, water band and foreground scroll at different rates, and all three frames are golden checkpoints.

The second criterion, Sonic 2's Emerald Hill Zone water ripple, is not verified. The Emerald Hill attract demo is the two-player version; its background renders plausibly, but the ripple wasn't compared frame by frame against a reference. The story stays "In progress" until it is.
