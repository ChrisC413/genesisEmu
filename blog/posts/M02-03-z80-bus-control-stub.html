Borrowing the sound CPU's memory

Before the Z80 runs a single instruction, the 68000 has to stop it, take over its bus and copy a sound driver into its 8 KB of RAM.

genesisEmu build notes4 min readStory M02-03

The Genesis has a second processor, a Zilog Z80 at about 3.58 MHz, whose usual job is sound. It has its own 8 KB of RAM and talks directly to the sound chips. But it can't load its own program, because nothing on its side holds code at power-on. The 68000 does that: it pauses the Z80, copies a sound driver into Z80 RAM, and releases it.

Running the Z80 was planned for M04. M02-03 only needed the 68000's side of the arrangement, so that games could get through boot. That meant the two control registers, Z80 RAM visible from the 68000, and somewhere for sound-chip writes to land.

Two registers that control a CPU

$A11100 is BUSREQ. The 68000 writes 1 to bit 8 to ask the Z80 to give up its bus, then polls the same bit, which reads 0 once the bus has been granted. $A11200 controls the Z80's RESET line: writing 0 holds the Z80 in reset, writing 1 lets it go. While the 68000 holds the bus, the Z80's memory appears in the 68000's address space at $A00000.

Both registers decode bit 8 of a word, which is bit 0 of a byte written to the even address. Games use both forms, so the bus extracts the bit either way:

The Z80's world, seen from the 68000

The state lives in a small struct, Z80ControlState: 8 KB of RAM, the two control bits, the bank register and the last value written to each sound-chip register. Keeping it all in one plain struct means the state hash (M02-05) and, later, save states can cover it.

Inside the 32 KB window at $A00000, the 68000 can reach:

  • Z80 RAM at $0000–$1FFF, mirrored up to $3FFF;
  • the YM2612 FM sound chip's four ports at $4000–$4003;
  • the bank register at $6000, which selects which 32 KB of 68000 memory the Z80 sees through its own window. It's loaded serially: each write shifts in one bit;
  • the PSG, the simpler square-wave chip, at $7F11.

In M02 the sound chips were stubs. Writes were remembered per register, and a status read of the YM2612 always said "ready", because a driver that waits for a busy flag to clear would otherwise hang. The real chips arrived in M05 behind the same interface.

The sound CPU can't load its own program. The 68000 has to pause it, write the driver into its memory, and let it go.

Breaking the rules is logged, not fatal

Touching Z80 space without owning the bus is a bug on real hardware. The access may collide with the Z80 and the result is unreliable. The emulator reports it as a Z80NotOwned issue with the PC of the offending instruction, and reads return open bus. If a game did this, the report would point straight at the instruction.

A deliberate simplification, later removed

On real hardware the grant takes a few cycles to arrive, and the 68000 is only supposed to access the Z80's bus while the Z80 is also out of reset. M02-03 made the grant immediate and ignored the reset line, and noted it as a simplification: none of the three games needed more. When the Z80 began executing in M04-07, the rule was tightened. Verified with Sonic's own sound driver

Unit tests cover the grant bit, RAM access with and without the bus, and word/byte behaviour. The real check was a [rom] test. After 600 frames of Sonic 1, Z80 RAM must contain more than 256 non-zero bytes, which is evidence that the game copied its sound driver across, through this code, exactly as it would on a console. The test checks only a count; the bytes themselves stay on the user's machine.
