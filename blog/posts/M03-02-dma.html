DMA, and the cost of a free copy

The VDP can copy memory into video RAM by itself, but while it does, the 68000 stops. M03-02 made that pause take as long as it does on hardware.

genesisEmu build notes4 min readStory M03-02

Copying graphics into VRAM one word at a time through the data port is slow: the 68000 has to read every word and write it again. So the VDP offers DMA (direct memory access). The program sets a source, a length and a destination, and the VDP does the copying itself. Sonic games use it constantly. In its first 600 frames, Sonic 1 issues 891 DMA transfers from 68000 memory to the VDP, moving 247,104 words, plus 8 fills. That covers palettes, the sprite table, scroll tables and animated art.

There are three modes:

  • 68000 to VDP: copy from ROM or RAM into VRAM, CRAM or VSRAM;
  • Fill: write one byte value over a range of VRAM, for clearing;
  • Copy: VRAM to VRAM.

M02 had already implemented all three as instant operations. M03-02 made them take time.

Why the timing matters

A 68000-to-VDP transfer uses the 68000's own bus, so the CPU is frozen until the transfer finishes. How long that takes depends on where the beam is. During active display the VDP is busy fetching pixels and can spare only a few slots per line. During vertical blank it can move much more. A game that starts a big DMA late in the frame finishes it in the next one, and the frame's timing changes: interrupts arrive at a different point in the code. To reproduce timing, the emulator has to freeze the CPU for the right amount of time.

Freezing the CPU, line by line

When a transfer starts, the VDP sets dmaActive and the scheduler stops running the 68000. Instead it hands the VDP the remaining time of the current line, lets it move as many words as fit, then moves on to the next line and repeats:

Lines are rendered as they end, so a DMA that spans active lines lands part-way through a frame. The top of the screen may still show old data while the bottom shows new data, as it would on hardware.

Inside runDma, partial words carry over between calls as a "credit" of byte × master-clock products. No fractional time is lost, and the transfer finishes exactly when the bandwidth says it should. As it runs, the length registers count down and the source registers count up, so a game that reads them mid-transfer sees plausible values.

A DMA that starts late in the frame finishes in the next one. The emulator has to know that, or the game's timing drifts.

The 128 KB wrap

The VDP's DMA source address is split across three registers, and only the low 17 bits count up. A transfer that crosses a 128 KB boundary wraps back to the start of the same 128 KB block instead of continuing. The core reproduces it:

Fill and copy

Fill and copy don't use the 68000's bus, so they don't freeze it. They still execute instantly in genesisEmu, but the status register's DMA busy bit stays set for their approximate duration (a fill moves one byte per slot, a copy two, since it reads and writes). A fill also waits for its data word: the transfer is armed by the command and starts on the next data-port write, which supplies the fill value.

Events for analysis

Every DMA raises the onDma hook with its kind, target, source, destination and length. That isn't needed to play a game. It's for the ROM map planned in M07, which will classify ROM regions by how they're used. A block that's the source of a DMA into VRAM is graphics; one that goes into CRAM is a palette. Unit tests check every field of the events for all three kinds, and gen_cli run prints per-kind counts.

What changed when timing arrived

Making DMA take time changes when everything else happens, so the boot-test state hashes from M02-07 all changed. They were updated in a dedicated [golden-update] commit, with the reason recorded in the M03 pull request: DMA timing shifts CPU timing, and the VDP state gained fields. Wait loops and fault counts were unchanged. The story also lists what isn't modelled yet: DMA and FIFO interaction, a separate rate for CRAM and VSRAM, and a known quirk with the last word of a DMA from RAM.
