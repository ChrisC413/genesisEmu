Where settings live, and how they survive upgrades

A JSON config that writes its own defaults, keeps keys it doesn't understand, and never leaves a half-written file behind.

genesisEmu build notes4 min readStory M00-03

Configuration and logging rarely get articles. They're plumbing. But every later feature uses them. The debugger saves window layouts, the input system saves key bindings, the CPU core logs illegal instructions, and the analysis tools store per-game data. If each of those invents its own storage, the result is a mess. M00-03 built that shared plumbing once.

Its code lives in gen_common, not in the emulator core. The core stays a pure, deterministic library. The app and the command-line runner each own a config file and a logger, and pass whatever the core needs into it.

Three folders, one rule

Settings belong where the operating system expects them. On Windows that is %APPDATA%\genesisEmu. On macOS it is ~/Library/Application Support/genesisEmu. Linux follows the XDG convention. The resolver is a pure function of the platform and an environment lookup, which makes it easy to test:

The override, GENESISEMU_HOME, matters more than it looks. Tests point it at a fresh temporary folder, so the app's first-run smoke test really is a first run, without touching the developer's own settings.

Every ROM also gets its own data folder: roms/<sha1> under the root. It's keyed by the SHA-1 of the de-interleaved ROM image, not by file name, so renaming sonic2.bin doesn't orphan its analysis data, and two different revisions of the same game never share a folder.

A config file that respects the future

The config is plain JSON, read with nlohmann-json and allowed to contain comments. Its behaviour follows three acceptance criteria.

Missing config writes defaults on first run. If there's no file, the loader writes one. New users get a file they can open and edit, and they don't have to guess which keys exist.

Unknown keys are preserved on save. This is the subtle one. Suppose a newer build adds a setting, and you then open an older build. A naive loader parses the file into a struct and writes the struct back, deleting the newer setting. genesisEmu keeps the parsed JSON document alongside the typed struct, and on save it only overwrites the keys it owns:

Old files are migrated. Every file carries a schemaVersion. A table of migration functions upgrades a version-N document to version N+1, applied in sequence. A file from a newer schema is left alone, with a warning that unknown settings will be preserved.

A bad value costs you that one setting. A corrupt file is moved aside, never silently overwritten.

Failing softly

Config files get hand-edited, and hand edits contain mistakes. The reader checks the type of every field. A string where a number belongs falls back to that field's default and adds a warning such as 'ui.windowWidth' has the wrong type; using the default, while every other setting still loads. If the whole file fails to parse, it's renamed to config.json.bad before defaults are written, so the user's work is never destroyed without a trace.

Writes are atomic in the everyday sense. The document goes to config.json.tmp first and is renamed over the real file only after the write succeeded, so a crash halfway through a save can't leave a truncated config behind.

Logging per subsystem

An emulator produces a lot of potential log output. You might want every VDP register write while debugging a rendering bug, and nothing from the CPU. genesisEmu creates one spdlog logger per subsystem: app, cpu, vdp, bus, audio, analysis, llm, config and cli. They all share the same sinks: coloured output on stderr and a rotating file, genesisEmu.log, whose size and count are configurable.

Levels come from the config: a default level plus a log.subsystems map, for example {"vdp": "trace"}. Unknown subsystem or level names produce warnings rather than errors. Each logger flushes on warnings and above, so the last lines before a crash reach the file.

How it is tested

The [config] tests cover first-run defaults, a disk round trip, unknown-key preservation, migration of unversioned files, newer-schema files keeping their version, wrong-typed fields, and corrupt files being moved aside. The [paths] tests run the Windows, macOS and Linux rules against fake environments, plus one test against the real environment of whichever machine runs it. The [logging] tests check level parsing, per-subsystem levels from the config, and that messages actually reach the rotating file.

One box stays unchecked: paths resolve correctly on both platforms. The macOS rule is unit-tested, but on Windows. Until it has run on a Mac, the story says so.
