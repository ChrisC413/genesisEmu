From framebuffer to screen, at 59.92 frames per second

The emulated console runs at 59.92 Hz and your monitor probably doesn't. Getting smooth video into the app meant a texture, some aspect-ratio arithmetic and two pacing strategies.

genesisEmu build notes4 min readStory M03-10

By M03-09 the core produced correct frames, but only the command-line tool could see them, as PNG files. M03-10 put them in the desktop app's game view, the empty panel created in M00-05, and made them move smoothly. It's the first story in the project written from the point of view of a player.

Framebuffer to texture

The VDP renders into an RGBA framebuffer in system memory, 320 pixels wide and up to 480 lines tall. After each emulated frame the app copies it into an OpenGL texture of the same size, uploading only the rows the current mode uses:

ImGui then draws the texture as an image, with texture coordinates that crop to the visible width and height. A 256-pixel-wide H32 frame and a 448-line interlaced frame share the same texture.

Scaling and aspect

Genesis pixels aren't square. On a 4:3 television, a 320-pixel line and a 256-pixel line fill the same width, so the pixels have different shapes in the two modes. The game view offers 4:3 aspect correction (on by default), which sizes the picture as lines × 4/3 wide, and square pixels when it's off. On top of that, fit scales to the largest size that fits the panel, and integer scales only by whole multiples, for crisp pixels. The picture is centred and letterboxed in whatever space the dock layout gives it. A right-click menu toggles these, plus linear filtering and a frame-time overlay.

The console runs at 59.92 Hz, not 60. Over a minute, that's about five frames of drift.

Pacing: two strategies

An NTSC Genesis produces 59.92 frames per second: 53.69 MHz divided by 896,040 master clocks per frame. Monitors run at 60 Hz, 144 Hz or anything else. The app picks between two strategies on every tick:

  • If the display's refresh rate is within 1 Hz of the console's, vsync drives the emulator. Every display refresh runs exactly one emulated frame, with no tearing and no uneven frame times. The 0.08 Hz difference is left to audio rate control, which arrived in M05.
  • Otherwise, an accumulator paces against the real clock. Elapsed time is added up, and a frame is emulated for every 1/59.92 s accumulated, up to four per tick, so a hiccup can't snowball into a long catch-up.

PAL machines use the same logic with 49.70 Hz.

Fast-forward

Reverse engineering involves a lot of waiting for the game to reach a particular point. Holding Tab (or a menu toggle, or --fast-forward on the command line) runs emulated frames unthrottled for about 12 ms of each UI tick, leaving time to draw the UI. The acceptance target was at least 5× real time. A smoke run of Sonic 3 & Knuckles peaked at 1,657 emulated frames per second, about 27×, with the core spending 0.62 ms per frame.

Controls and the smoke test

The Emulation menu gained Run/Pause (F5), Reset and Fast-forward. The app owns a Machine, created when a ROM is opened, with a --lock-on= option to stack Sonic & Knuckles and Sonic 3 the way the cartridges combine. The M00-05 smoke test became stricter: with a ROM loaded, it now fails unless frames were actually emulated and reached the game view, and it logs the frame hash. A local run of Sonic 1 for 1,300 frames averaged 0.66 ms of core time per frame.

Not verified yet

The story's first criterion, no tearing and steady pacing on a 60 Hz display, is open for a mundane reason. The development machine's display runs at about 100 Hz (the smoke test measured 99.9 ticks per second with vsync), so the vsync-locked path was never exercised. The clock-paced path ran instead. The aspect criterion was checked on a screenshot from a local run. The view settings weren't saved between runs in this story; persisting them came with M04's configuration work.
