M02 · System bus & boot · Story 7 of 7

Three games boot, with nothing on screen

Before there were any graphics, genesisEmu could prove that Sonic 1, Sonic 2 and Sonic 3 & Knuckles boot to their main loops, identically every time. The test doesn't know anything about the games.

genesisEmu build notes4 min readStory M02-07

At the end of M02 the emulator had a CPU, a bus, I/O registers, Z80 control, a video chip that drew nothing and a scheduler. Did it all work together? The milestone's exit criterion was concrete: Sonic 1, Sonic 2 and Sonic 3 & Knuckles should boot headless to their main loop, deterministically, without a single fault. M02-07 turned that into automated tests.

What "booted" means without a screen

With no picture there's no title screen to look at. The test needs observable facts that only hold for a game that booted correctly:

  1. No faults. Over 600 frames (ten seconds of game time), the 68000 must not take a single address error, illegal instruction, zero divide or similar exception. These are counted by the scheduler's statistics from M02-05.
  2. It's in its wait loop. A Genesis game that has finished booting does its frame's work and then spins in a tiny loop until the vertical interrupt sets a flag. If the emulator is healthy, the V-int keeps interrupting the same few bytes of code.
  3. It's deterministic. Two runs produce bit-identical state.

Finding the wait loop without knowing the game

The easy way to check point 2 would be to hard-code each game's loop address from a community disassembly. The project avoided that: the test would then know things about the games that the emulator is meant to discover. Instead the test infers the loop from behaviour alone, using the PC that each V-int interrupted:

  • Over the last 60 of the 600 frames, at least 90% of frames must take exactly one V-int.
  • At least 90% of those V-ints must interrupt a window of code smaller than 16 bytes, found as the most common interrupted PC plus its close neighbours.
  • Over 5 more frames, an instruction inside that window must read a work-RAM byte that the V-int handler writes, with the CPU's interrupt mask at 6. That's the "V-int happened" flag the loop is polling.

If the two sets share an address, the loop really is waiting for the interrupt, rather than just being stuck somewhere small. The detection logic contains nothing specific to Sonic; it would work for any game with the usual structure.

The test finds each game's wait loop from behaviour alone. Recorded addresses only check afterwards that the result hasn't moved.

Golden numbers, no golden bytes

ROM tests can't ship ROMs, and they mustn't ship anything derived from a ROM's code either. The golden file, tests/golden/m02_boot.json, holds only numbers per game: the SHA-1 used to find the ROM in the user's folder, the address window where the wait loop was found, and the state hash after 600 frames. The test then checks that the detected loop lies inside the recorded window and the hash matches.

Under 0.2 ms per emulated frame means the core, without graphics yet, ran these games roughly 90 times faster than real time. S3K is assembled with the lock-on helper from M00-04 (Sonic & Knuckles followed by Sonic 3), as the cartridge stack would present it.

When a later change legitimately alters emulation (M03's DMA timing, for example, which freezes the 68000 during transfers), the hashes in this file change in a separate commit tagged [golden-update] with a reason, as spec 13 requires. A changed hash never slips in with unrelated work.

Hashing state portably

A state hash only proves determinism if it's computed the same way everywhere. StateHasher wraps XXH3-64 and accepts only explicitly serialised fields, each written as little-endian bytes, with a four-character tag per component so that, for example, VDP fields can't alias RAM bytes:

One acceptance box remains open: state hash identical on Windows and macOS. The design should guarantee it, but no Mac has run the tests yet, so the story stays "In progress" until tools/validate-roms.sh confirms the Windows hashes on a Mac.

In CI, without the games

The [rom] tests need the user's dumps, so in CI the test binary exits with code 4 and CTest reports it as skipped. Determinism is still checked on every push using the synthetic boot ROM, through the [determinism] unit test and cli.run_boot_json, which runs the CLI twice and compares the state hashes.

None of the three games waited on the Z80 during those 600 frames, so no workaround was needed. That was a relief, because the Z80 didn't execute yet. It does from M04.
