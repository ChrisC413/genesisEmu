Testing on macOS without paying for macOS CI

When the free CI tier has no Mac runners, the Mac check becomes a script that you run yourself and paste into the pull request.

genesisEmu build notes4 min readStory M00-07

genesisEmu targets two desktop platforms, Windows 11 and macOS, but its CI runs on only one. Decision D-016 limits CI to GitHub's free windows-latest runners. macOS runners are billed at a premium, and this is a personal project. Dropping macOS wasn't acceptable, and neither was finding out about a broken Mac build three milestones late.

M00-07's answer is a single script, tools/validate-mac.sh, which does on a Mac what CI does on Windows, plus a bit more. Its last step prints a summary that goes into the pull request.

What the script does

It starts by refusing to run in the wrong place. It checks that it's on Darwin, that CMake, CTest and the Xcode command-line tools are installed, and that VCPKG_ROOT points at a real vcpkg checkout. Each missing piece produces a one-line error that says how to fix it.

Then it configures, builds and tests the mac-release preset with warnings as errors, the same test set CI runs on Windows. Next comes a second full build, mac-asan, with AddressSanitizer and UndefinedBehaviorSanitizer, and the tests run again. This is the one check the Mac does better than Windows CI. An emulator does a lot of array indexing driven by guest data: a tile index read from video memory, a register number decoded from an opcode. Sanitizers catch an out-of-bounds read the moment it happens rather than when it corrupts something three frames later.

The Mac script adds the one check Windows CI doesn't have: a full test run under AddressSanitizer and UBSan.

Finally it ad-hoc signs the .app bundle and verifies the signature strictly, then checks that the executable and icon are where the bundle says they are. A broken bundle is the kind of failure no unit test notices.

Keeping going after a failure

A naive script would use set -e and stop at the first error. This one uses set -uo pipefail without -e and tracks failures itself, so a failing release test doesn't hide whether the sanitizer build is also broken. A summary that matches the template

The output that matters is the block at the end: commit (with a note if the tree has uncommitted changes), macOS version and build, CPU architecture, the clang version, build and test results for each configuration, the bundle check, the duration and an overall PASS or FAIL.

The pull request template contains the same block with the values left empty, and the field names match exactly. That was the one acceptance criterion that could be verified without a Mac. Turning CTest's output into "N passed, N failed, N skipped of N" meant parsing CTest's summary line, whose wording varies between CTest versions. The parser accepts both the old and new wording and was tested against real CTest output.

When the check is required

CONTRIBUTING.md spells out when a pull request needs the Mac block: changes to platform code under src/app/platform, to CMake, presets or the vcpkg manifest, or to the audio and video backends. A change to the 68000 instruction decoder needs only Windows CI. Its tests are platform-neutral C++, and the Mac run would only repeat them.

ROM tests, the same idea

The same story added tools/validate-roms.sh and tools/validate-roms.ps1. Tests that need commercial games are tagged [rom] and look for dumps in the folder named by GENESIS_ROM_DIR. Those ROMs can never be in the repository or in CI, so these scripts are the way to run that tier on either OS, and the PR template has a checkbox for them too.

Honest status

At the time the story was written no Mac was available. The script was syntax-checked with bash -n, but the criteria "runs from a clean clone on macOS 15+" and "non-zero exit on any failure" stayed unchecked, and the story is still "In progress". The risk it guards against is real. The VDP milestone's pull request later broke the Mac build through libc++'s per-macOS-version feature gates, which Windows CI could not see. The fix became decision D-025: raise the macOS minimum to 15.0.
