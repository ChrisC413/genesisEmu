Decimal arithmetic on a binary chip

Score counters and timers on the Genesis are often binary-coded decimal. ABCD, SBCD and NBCD are three instructions with flags the manual calls undefined.

genesisEmu build notes4 min readStory M01-07

Look at a Sonic HUD: score, time, rings. Each number has to be shown as decimal digits, and turning a binary number into decimal digits needs division, which costs over a hundred cycles on a 68000. Many games avoid that by storing such numbers in binary-coded decimal (BCD) in the first place: each 4-bit nibble holds one decimal digit, so the byte $59 means fifty-nine. Drawing it is a matter of looking at each nibble.

The 68000 supports this directly with three instructions: ABCD (add decimal with extend), SBCD (subtract decimal with extend) and NBCD (negate decimal). They work on single bytes, two digits at a time, and chain through the X flag for longer numbers. M01-07 implemented them, including the flags Motorola documented as undefined.

Add in binary, then correct

Inside the chip, BCD addition is ordinary binary addition followed by a correction. Adding $08 + $05 in binary gives $0D. That isn't a valid decimal digit, so the chip adds 6, giving $13: thirteen, carry into the tens digit handled. The same happens for the tens digit with $60. "Undefined" in a manual doesn't mean random. The chip does something specific, and software can come to depend on it.

Undefined, but not random

Motorola's manual says the N and V flags are undefined after these instructions. That doesn't mean they're random. A given chip produces a specific, repeatable result, and the SingleStepTests suite recorded it. An emulator that leaves those flags alone, or clears them, fails thousands of vectors. More to the point, any game code that accidentally branches on them would behave differently.

The rule the core settled on reproduces every vector. N is simply bit 7 of the corrected result. V is set when the decimal correction itself flipped bit 7: on addition, the binary sum had bit 7 clear and the corrected result has it set; on subtraction, the reverse. That's the last argument to setBcdFlags above.

Two flags behave like the extended binary instructions from M01-05. C and X carry the decimal carry or borrow out of the byte, so multi-byte numbers can be chained. Z is only ever cleared, never set. That's what makes a chain of ABCDs over a 6-digit score correctly report "the whole number is zero".

Two operand forms

Each instruction comes in a register form (abcd.b d0,d1) and a memory form using pre-decrement on both operands (abcd.b -(a0),-(a1)). The memory form exists for exactly the multi-byte case: point two address registers just past the ends of two BCD numbers and repeat the instruction to walk down through the bytes, least significant first, with X carrying between them.

The memory form has its own ordering details. It spends 2 internal cycles, decrements and reads the source, decrements and reads the destination, prefetches the next instruction, and only then writes the result. As elsewhere in the core, that order is what makes faulting cases come out exactly right. A7 decrements by 2 for these byte operations, the same stack-alignment rule as the addressing modes.

Inputs that aren't valid BCD

Nothing stops a program from passing $FF to ABCD. The chip still runs its add-and-correct sequence and produces some byte. Because the core implements the same steps rather than "convert to decimal, add, convert back", invalid inputs produce the same results as on the chip. The test vectors use random bytes, so most of them are exactly such invalid inputs, and the core matches them.

Verified

ABCD, SBCD and NBCD pass 100% of their 24,195 SingleStepTests vectors, including the undefined N and V flags and every cycle count. The disassembler's golden-text tests check the two syntactic forms, for example abcd.b -(a0),-(a1) and sbcd.b d0,d1.
