Every way to find an operand

The 68000's addressing modes are where most of the instruction set's complexity lives. Written once as templates, they serve every instruction.

genesisEmu build notes5 min readStory M01-03

Most 68000 instructions don't care where their operands come from. ADD adds, whether the source is a register, a memory location pointed to by a register, a constant in the instruction stream or a table entry indexed by another register. The "where" is the job of the effective address (EA): a 6-bit field in the opcode, made of a 3-bit mode and a 3-bit register number, that picks one of twelve addressing forms. (The story says fourteen; how many you count depends on how you group them. The opcode field encodes the twelve below.)

Get the EA logic right once and every instruction that uses it is right. Get it subtly wrong, for example by incrementing a register at the wrong moment, and the bug shows up in hundreds of instructions. M01-03 implemented the modes as one shared path.

Templates instead of switches

The obvious implementation is a function with a big switch on the mode, called for every operand of every instruction. That costs a branch per operand and buries the mode-specific behaviour in one huge function. genesisEmu makes both the operand size S (1, 2 or 4 bytes) and the mode M template parameters:

When the decode table is built, a helper called byMode turns the run-time mode of each opcode into the matching compile-time instantiation. The result is one specialised handler per size/mode combination. MOVE is the extreme case, with a source mode and a destination mode, and gets a handler for every valid pair.

A byte pushed onto the stack still moves the stack pointer by two. The chip keeps A7 word-aligned, and so must the emulator.

The quirks that matter

A7 and bytes. (A0)+ on a byte operand adds 1 to A0. On A7, the stack pointer, it adds 2, because the 68000 keeps the stack word-aligned. Look for reg != 7 in the excerpt above. Get this wrong and the first byte-sized push corrupts the stack.

Index registers can be words or longs. In d8(An,Xn) the extension word picks the index register and whether to use all 32 bits or only the low 16, sign-extended. Sign extension is the classic bug here: index a table with D0.W = $FFFE and the correct offset is −2, not 65,534.

PC-relative means relative to the extension word. During execution the core's PC points at the word in the prefetch register, which is the base the hardware uses for d16(PC). Because the core models the prefetch queue, the base falls out naturally.

abs.W is sign-extended. ($F600).w doesn't mean address $00F600. It means $FFF600, the top of the 24-bit address space, where the Genesis keeps its 64 KB of work RAM. Sonic code uses this short form constantly to reach RAM variables in two bytes instead of four.

Address errors are detected here

A word or long access to an odd address makes the 68000 raise an address error. The check sits in the lowest-level bus primitives, so it applies to every EA mode automatically. It throws a small C++ exception that step() catches and turns into the correct exception frame, which M01-10 completes. Long accesses are always issued as two word accesses, because an odd long access must fault on its first word, before anything is written.

Timing and verification

EA time isn't looked up in a table. It's the sum of what happens: 4 cycles per extension-word fetch, 4 cycles per operand word, plus 2 internal cycles for -(An) and the indexed modes. The acceptance criterion asked for the EA cycle table to match the 68000 User's Manual. The check used was MOVE, which combines every source mode with every destination mode. The SingleStepTests files for MOVE.b, MOVE.w and MOVE.l, plus LEA, PEA, JMP and JSR, which use the "control" addressing modes, all pass at 100%, with zero cycle mismatches.

From here on, adding an instruction mostly means writing what it computes. Where its operands live and what that costs is already handled.
