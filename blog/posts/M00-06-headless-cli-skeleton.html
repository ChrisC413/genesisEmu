An emulator you can drive from a script

gen_cli started as three subcommands and a table of exit codes. It became the way every later milestone is tested.

genesisEmu build notes4 min readStory M00-06

A desktop window is how a person uses an emulator. Scripts, CI and analysis tools need something else: a program they can start with arguments, that does its job without a display and reports through its exit code and standard output. That program is gen_cli, and M00-06 created its skeleton.

The story was small. It asked for argument parsing, an info command, a run command that did nothing yet, a --help that documents every subcommand, and four exit codes. The design choices made here decided how the rest of the project gets tested.

A contract made of exit codes

The exit codes are part of the interface, so they're defined once, at the top of the file:

The split matters. A usage error (1) means the caller made a mistake, such as an unknown option, a missing --rom or --frames ten. A load error (2) means the input was bad: a missing file, a ROM that's too small, a Master System image. A check failure (3) means the tool ran correctly and found a problem. In M00 nothing used code 3 yet. Later milestones use it for a 68000 fault exception during a run, a golden frame that doesn't match, or an audio hash that changed. A CI job can tell "the test harness is broken" from "the emulator regressed".

One formatter, two front-ends

gen_cli info --rom game.bin prints the same ROM description that the desktop app's ROM Info panel shows. Both get it from one place: gen_common turns a parsed Rom into a list of label/value pairs (describeRom) or a JSON object (romToJson). The CLI just aligns the labels:

With --json the same data comes out as JSON, ready for another program to parse. Sharing the formatter means the app and the CLI can never disagree about what a header field says.

The CLI is the emulator's test interface. Almost every later acceptance criterion is checked by running it.

Testing a command-line tool with CTest

Each CLI test case is one line in tests/cli/CMakeLists.txt: a name, an expected exit code, the arguments, and optionally a regular expression the output must match. A helper function expands that into a CTest test that runs a small CMake script, run_cli.cmake, which executes gen_cli and checks both.

The COMPARE option runs a second command and requires a chosen piece of output (by default the SHA-1 line) to be identical in both. That one mechanism checks that SMD and BIN give the same hash, and later that two runs of the same ROM give the same state hash.

The test ROMs aren't commercial games. A fixture, cli.make_test_roms, runs first and writes synthetic images into the build folder: a normal BIN, the same image interleaved as SMD, a too-small file, and later a small bootable program. Every other CLI test declares that fixture as a requirement, so CTest orders them correctly even in parallel runs.

The skeleton grows

When M00 closed, run loaded a ROM and returned 0 without emulating anything. It existed so scripts and tests could be written against the interface before the machine was. Its help text has grown with every milestone since. run now emulates N frames and prints instructions per frame, the deterministic state hash and any CPU faults. It can dump frames as PNG, compare them against golden checkpoints, replay scripted controller input, load and save SRAM, record a WAV file and write a log of sound-chip register writes. A trace command writes instruction traces.

The original fifteen cli.* cases still run, joined by many more. Typical of the later ones, cli.run_faulting_rom runs a ROM that isn't a valid program and expects exit code 3 with the message faults N: first vector ..., and cli.help checks that the help text mentions every command and the exit codes.

Small decisions that paid off

  • Errors go to stderr, data to stdout. gen_cli info --json | jq .sha1 works even when the loader prints warnings.
  • Warnings aren't failures. A header checksum mismatch is logged through the cli logger and the command still exits 0, the same policy as the loader itself.
  • Unknown options are errors. A typo like --frmaes exits 1 with "unknown option" instead of being silently ignored, so a test can't pass by accident.

None of this is glamorous. But when M02 needed to show that three games boot the same way twice, M03 needed golden frames, and M05 needed audio hashes, the harness was already there.
