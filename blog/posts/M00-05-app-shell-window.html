A window with room for a workbench

SDL3, OpenGL 3.3 and Dear ImGui's docking branch give every future debugger panel a home. A smoke test checks that it actually renders.

genesisEmu build notes5 min readStory M00-05

A typical emulator shows one thing: the game. genesisEmu will eventually show a dozen things at once, including CPU registers, memory viewers, a disassembly that follows the program counter, VDP tile viewers and a colour-coded map of the ROM. The application shell built in M00-05 was designed for that future. At the time it held just two panels, an empty game view and a ROM information panel.

The stack

Decision D-001 picked C++20, SDL3 and Dear ImGui on its docking branch. ImGui is an "immediate mode" GUI library: instead of building a tree of widget objects, the program describes the whole UI from scratch every frame, and ImGui works out what changed. That suits debugging tools very well. A register view is just a function that prints the registers every frame. There's no state to keep in sync with the emulator.

SDL3 creates the window and handles input, and OpenGL 3.3 core renders ImGui's draw lists. The story allowed either OpenGL or SDL's newer GPU API. OpenGL 3.3 won because it runs on both target platforms, and its shaders are pinned to GLSL #version 150 so the same shader source compiles on macOS's core-profile driver.

A context request can "succeed" and still hand back something useless. On headless Windows machines some drivers, such as Windows' GDI fallback, hand out a legacy context anyway. The window code therefore reads the version string after creating the context, and fails with a clear message if the major version is below 3.

Hi-DPI: think in logical pixels

On a 150%-scaled laptop or a Retina display, a UI drawn at "100 pixels" is tiny unless something scales it. The shell asks SDL for the display's content scale, multiplies the window size by it, and passes the same factor to ImGui's style and font scale (ScaleAllSizes and FontScaleDpi). On macOS the bundle's Info.plist sets NSHighResolutionCapable. The code paths exist, but the acceptance box for crisp rendering at 150% stays unchecked: only a 100% display was available.

Docking, saved in the config

ImGui normally saves window positions to an imgui.ini file next to the executable. That conflicts with M00-03's rule that settings live in one JSON config in the user's data folder. The fix is a single line: turn off ImGui's own file and round-trip the layout through memory.

On start-up the saved string is fed to ImGui::LoadIniSettingsFromMemory. When ImGui reports a change, SaveIniSettingsToMemory captures the current layout back into the config. On first run, or after Help > Reset Layout, there is nothing to restore, so the dock builder creates a default: the game view in the centre and ROM info in a column on the right.

Menus, dialogs and recent files

The menu bar was laid out for the whole project from the start, with File, Emulation, Debug, Analysis and Help menus, even though most items didn't exist yet. File > Open ROM uses SDL3's native file dialog, so Windows users get the Windows dialog and Mac users the Mac one. Files can also be dropped onto the window. Every successful open goes to the top of a Recent ROMs list stored in the config and capped at a configurable length.

Opening a ROM fills the ROM Info panel with the parsed header from M00-04: titles, serial, region, ROM and RAM ranges, SRAM declaration, header and computed checksums, SHA-1, CRC32 and the identified game.

The packaging is per platform. Windows gets an executable with an embedded icon from a resource file. macOS gets a proper .app bundle, with the icon, version and bundle identifier set from CMake.

A GUI test that can't see the screen still knows whether its panels are docked, its layout was restored and its ROM was loaded.

Testing a GUI without looking at it

GUI code is notoriously hard to test automatically. genesisEmu's approach is a built-in self-check. Launched with --smoke-test=N, the app renders N frames and then inspects its own state before exiting:

CTest runs it twice in a row against a synthetic ROM, with GENESISEMU_HOME pointing at a fresh folder. app.smoke_first_run checks a genuine first launch: defaults written, default layout docked, ROM loaded. app.smoke_layout_restored then runs with --expect-restored-layout and fails unless the layout saved by the first run was loaded back. That run also takes a PNG screenshot with --screenshot=, which was inspected by hand on Windows. The smoke check grew with the project, and since M03 it also verifies that frames were emulated and reached the game view.

Exit codes keep this honest in CI. The app returns 77 when it can't get an OpenGL 3.3 context, and CTest is told that 77 means "skipped". On GitHub's GPU-less runners the smoke tests show as skipped rather than passing, while on any developer machine they run for real.

What is still open

The story is "In progress" for documented reasons. macOS launch is unverified, the display refresh rate wasn't measured (vsync is on), Hi-DPI is untested, and interactive drag-and-undock was never driven by a test. Restoring the layout is covered automatically; dragging panels around isn't. The story file lists each of these separately.
