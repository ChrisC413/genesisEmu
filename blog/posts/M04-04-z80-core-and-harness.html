A second CPU, and two ways to check it

The Z80 got the same treatment as the 68000: a skeleton first, then harnesses for 1.6 million recorded test vectors and a pair of 1980s CP/M exerciser programs.

genesisEmu build notes4 min readStory M04-04

The Genesis's second processor is a Zilog Z80, the same chip at the heart of the Master System, the ZX Spectrum and many arcade boards. On the Genesis it runs the sound driver: reading music data, feeding the FM synthesizer and streaming drum samples. Like the 68000, the project requires it to be hand-written. M04-04 built its skeleton and, more importantly, the means of proving it correct.

The skeleton

The structure mirrors the 68000 core from M01. Z80State holds every register in a plain struct, including several that only matter for exactness:

WZ (also called MEMPTR) is an internal register that programs can't read directly, yet it leaks into two undocumented flag bits after certain instructions. Q records whether the previous instruction wrote the flags, which a pair of instructions depends on. These are the kind of details M04-05 has to get right, and the skeleton had to have room for them.

BusZ80 is the Z80's view of the world: memory reads and writes, I/O ports (unconnected on the Genesis, reading $FF), the byte on the data bus during an interrupt acknowledge, and a wait-state counter, the same pattern as the 68000's bus. step() executes one instruction and returns T-states, the Z80's clock cycles. The same Hooks struct reports instructions, accesses and interrupts, tagged CpuId::Z80 with Z80-local addresses.

Unlike the 68000's 65,536-entry table, the Z80 decodes with a switch on the opcode byte, split by prefix: unprefixed, CB (bit operations), ED (extended), DD/FD (which redirect HL to the IX or IY index registers) and the doubly prefixed DDCB/FDCB. An 8-bit opcode space is small enough that a switch is clear and fast.

Harness 1: SingleStepTests

The SingleStepTests project has a Z80 suite in the same spirit as the 68000 one: for each opcode, a file of recorded vectors with initial state, final state, memory, port activity and cycle count. The fetch script downloads 1,604 opcode files (pinned to a commit) and converts them to a compact binary format. gen_z80_sst runs each vector on a flat 64 KB bus and compares everything:

As with the 68000 harness, there's a self-test: --inject-fault corrupts the result and --expect-fail requires the runner to notice. The story notes that the 68000 runner's code wasn't shared after all. The formats differ enough that a common reader would only share the header check.

ZEXALL is a 1980s CP/M program that tests a Z80 against itself. To run it, the emulator pretends to be a CP/M computer for long enough to print its results.

Harness 2: ZEXDOC and ZEXALL

Long before recorded test vectors existed, Z80 emulator authors used ZEXDOC and ZEXALL, instruction exercisers written for the CP/M operating system. They run each group of instructions through many operand combinations, hash the resulting CPU states with a CRC, and compare with CRCs recorded on real hardware. ZEXDOC checks documented flags only; ZEXALL includes the undocumented ones.

They expect to run under CP/M, but they only use two services: print a character and print a string. gen_z80_zex fakes just enough of CP/M. A jump to $0000, CP/M's warm boot, ends the run. The runner counts "OK" and "ERROR" lines in the output and exits accordingly.

Where they run

The SingleStepTests suite takes about 2 seconds in Release, so the Release CI job runs all of it on every push, and Debug runs 100 vectors per file. ZEX is different: each program executes about 5.76 billion instructions, roughly 80 seconds. M04 added a nightly workflow, nightly.yml, on the free tier's standard runner, that runs both under the CTest label z80-zex, which the normal presets exclude.
