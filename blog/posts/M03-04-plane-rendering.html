The first pixels: tiles, name tables and planes

The Genesis has no framebuffer. It builds every line from 8×8 tiles arranged by tables in video memory. M03-04 taught genesisEmu to do the same, and the SEGA logo appeared.

genesisEmu build notes4 min readStory M03-04

Modern graphics hardware draws into a framebuffer: a block of memory with one entry per pixel. The Genesis doesn't have one. Its VDP generates the picture on the fly, line by line, from compact descriptions in VRAM. There are two scrolling background planes, A and B, built from 8×8-pixel tiles, plus sprites on top. M03-04 implemented the planes, the foundation every other rendering story builds on.

Tiles

A tile is 8×8 pixels at 4 bits per pixel, so 32 bytes. Each pixel is an index from 0 to 15 into one of the four 16-colour palette lines in CRAM. Index 0 is transparent. Pixels are packed two per byte, with the leftmost pixel in the high nibble:

Name tables

A plane is a grid of tiles, described by a name table in VRAM with one 16-bit entry per cell:

Planes can be 32, 64 or 128 cells wide and tall, set by register 16. That's larger than the screen, which is what makes scrolling possible (M03-05). The size code 2 is prohibited by the documentation; the emulator treats it as 32 cells, and name-table addresses wrap inside 8 KB, which reproduces how the hardware mirrors invalid size combinations.

Rendering a line

The renderer runs once per line, at the line's end (see M03-03). For each plane it works out which row of the plane this screen line shows, walks along the line, fetches each name-table entry, applies the flips, and reads tile pixels:

The renderer doesn't produce colours straight away. It produces "pixel codes" and decides colours only after all the layers have been compared.

Pixel codes, then colours

A key design decision: the plane renderer doesn't write colours. It writes one byte per pixel into a line buffer, a pixel code holding the priority bit, the palette line and the colour index:

Plane B, plane A and the sprites each get their own buffer. Only once all three exist does the composer pick a winner for each pixel and look its colour up. That separation is what makes priorities (M03-08) and shadow/highlight possible later without rewriting this code. It also keeps the priority bit of transparent pixels, which the shadow logic turns out to need.

From CRAM to RGB

A CRAM colour has 3 bits per channel. Converting to 8-bit RGB isn't a simple multiplication, because the console's video DAC isn't linear. genesisEmu uses a 15-step ramp: normal colours use the even steps, and shadow and highlight (M03-08) use the lower and upper halves. The story labels the values as approximate measurements, not exact.

The 64 CRAM colours are converted into a cached table of RGBA values in all three intensities, rebuilt only when CRAM changes. Because the cache is checked at the start of every line, a palette change made mid-frame lands on exactly the line it should.

Odds and ends

The output is an RGBA framebuffer 320 pixels wide (256 in H32 mode) and 224 or 240 lines tall. When display is disabled, a line shows only the backdrop colour (register 7). Register 0 can blank the leftmost 8 pixels, which games use to hide scrolling artefacts at the screen edge. Vdp::frameHash() hashes the visible part of the framebuffer, which the golden-frame tests in M03-11 use.

Verified

Unit tests in tests/unit/vdp_render_test.cpp build synthetic VRAM contents and check pixel order, palettes, both flips, plane sizes, wrapping, the backdrop, display disable and left-column blanking. For the real games, gen_cli run --dump-frames wrote PNGs that were checked by eye: the SEGA logo at frame 150 and Sonic 1's title screen at frame 600, with its sky, clouds, mountains, emblem, banner and water. Both frames' hashes became golden checkpoints. The images themselves stayed on the developer's machine.
