Every Z80 opcode, including the ones Zilog never documented

1,604,000 test vectors and both ZEX exercisers pass, with no exclusions. Getting there meant modelling two flag bits Zilog never documented and a hidden register that leaks into them.

genesisEmu build notes4 min readStory M04-05

The Z80 instruction set is old and well studied, but "well studied" includes decades of discoveries about behaviour Zilog never documented. Code written against real chips can depend on that behaviour, on purpose or by accident, and an emulator can't know in advance which parts a given sound driver uses. M04-05 implemented everything and checked it against two independent references.

The headline result: 1,604,000 of 1,604,000 SingleStepTests Z80 vectors pass, with no exclusions, and ZEXDOC 67/67 and ZEXALL 67/67. The core is hand-written from public documentation: Zilog's user manual, Sean Young's "The Undocumented Z80 Documented", and published research on MEMPTR and the block instructions.

Decoding by bit fields

Z80 opcodes have a regular structure when you split the byte into fields: two bits x, three bits y and three bits z. In the unprefixed range $40–$7F, every opcode is LD r,r' with y as destination and z as source, except $76, which would be "LD (HL),(HL)" and is HALT instead:

Prefixes change the meaning of register numbers. With a DD prefix, "HL" becomes IX, "H" becomes the high byte of IX (an undocumented register usually written ixh), and (HL) becomes (IX+d) with a displacement byte. But in LD r,(IX+d), the other register stays a real H or L. The code handles that with separate "raw" register accessors, as the comment above notes.

Bits 3 and 5

The Z80's flag register has two bits that Zilog documented as unused. They aren't. After most instructions, bits 3 and 5 (called X and Y) are copies of bits 3 and 5 of some internal value, usually the result, sometimes an operand, sometimes something stranger. A shared table precomputes S, Z, X and Y (and optionally parity) for every byte value, which most ALU operations use directly.

The "something stranger" cases are where the work was. BIT n,(HL) takes X and Y from the high byte of WZ, a hidden internal register (also called MEMPTR) that holds addresses computed by earlier instructions. Programs can't read WZ, but they can see its high byte through those two flag bits, so the core tracks WZ through every instruction that updates it.

Two flag bits Zilog called "unused" turn out to expose a hidden register, so the emulator has to track that register through every instruction.

The Q latch

The strangest case, discovered relatively recently, involves SCF and CCF (set and complement the carry flag). Their X and Y bits depend on whether the previous instruction modified the flags. The core tracks this as Q: after each instruction, Q is the new F if the instruction wrote the flags, otherwise 0.

Block instructions

LDIR, CPIR, INIR and OTIR repeat until a counter runs out. On real hardware each repetition is a separate instruction execution that rewinds the PC by 2, which is why an interrupt can arrive in the middle of a long copy. The core does the same. A repeating step returns 21 T-states and leaves PC on the instruction; the final one returns 16. Interrupts, HALT and the R register

The Z80 has three maskable interrupt modes. In IM 0 it executes whatever byte is on the data bus. The Genesis leaves the bus pulled up, so that byte is $FF, which is RST 38h, the same destination as IM 1. IM 2 builds a vector address from the I register and the bus byte. The non-maskable interrupt (NMI) is also implemented. EI delays interrupt acceptance by one instruction, and an interrupt accepted right after LD A,I or LD A,R clears the P/V flag (a bug of the original NMOS chip), both modelled.

HALT leaves PC after the instruction and then executes internal NOP cycles until an interrupt, incrementing the 7-bit refresh counter R each time, as the hardware does. R counts every opcode fetch (M1 cycle), including prefixes. Its top bit only changes through LD R,A.

Results

The SingleStepTests suite (commit ebe1875d) compares every register, including WZ, R, Q and the EI and LD A,I latches, plus RAM, port writes and T-states: 1,604,000 of 1,604,000 vectors pass in about 2 seconds. ZEXDOC and ZEXALL each run about 5.76 billion instructions in roughly 78 seconds in Release, around 75 million instructions per second, and report 67 of 67 tests OK. The Release CI job runs the full vector suite on every push; the ZEX programs run nightly.
