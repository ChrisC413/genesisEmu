A line of text for every instruction

When a game misbehaves in an emulator, the fastest way to find out why is to log every instruction and compare it with a reference. genesisEmu's trace format is built for diffing.

genesisEmu build notes4 min readStory M02-06

Bringing up an emulator means finding bugs whose effects show up long after their cause. A wrong flag in frame 3 changes a branch, which leaves a variable unset, which crashes in frame 40. Looking at the crash tells you little. The reliable technique is an instruction trace: log every instruction the CPU executes with its effects, do the same in a trusted emulator, and find the first line where the two disagree. That line is usually the bug.

M02-06 added this to genesisEmu as gen_cli trace, along with a format designed for diffing and a tool to do the diffing.

The format

Each executed instruction, and each interrupt entry, becomes one line of text. Here are the first lines of the golden trace of the project's own synthetic boot ROM:

The second line reads the version register and gets $A0, the NTSC Americas value from M02-02. The branch skips ahead, and the next line asks for the Z80 bus (M02-03), and the trace shows the word written to $A11100. Each layer built so far is visible in a few lines of text.

Some deliberate choices make the format good for diffing:

  • Register deltas, not full dumps. Only registers that changed are listed, in a fixed order. Lines stay short, and a difference in a register stands out.
  • Memory writes in bus order, as W.B or W.W with address and value. A long write appears as two word writes, as it does on the bus. At most 16 are listed, then +N.
  • Fixed-width columns and LF line endings, so standard tools such as diff and grep work, and so does reading by eye.
  • Interrupt entries are records too: interrupt level 6 with the stack writes and the interrupted PC, so a trace shows exactly where V-ints land.

The full specification is a table in docs/specs/08-debugger.md under "Text trace format (v1)", and the file starts with a version header, so future format changes can be detected.

Two traces that should be identical are diffed line by line. The first difference is usually the bug.

How the writer attaches

The trace writer lives in gen_instrument, not in the core. It installs itself through the same Hooks struct from M01-01: onInstr to start a record, onAccess to collect writes, and onIrq for interrupt entries. With no writer attached, the core pays nothing beyond its existing null-pointer checks. The writer gets its disassembler as a callback that gen_cli passes in, so the instrumentation library doesn't depend on the analysis library.

Filters keep traces manageable: a frame range (--start-frame, --frames), a PC range (--pc lo-hi), "first execution only" (--first, which logs each address once and is a quick way to see which code ran at all) and a record limit. Output is buffered and written in large blocks. A trace of Sonic 1's first 11 frames is 163,613 records and 18 MB, and takes 0.16 seconds. Traces of commercial games are never committed; they contain the game's code.

trace-diff

tools/trace-diff.py compares two traces record by record and prints the first divergence with some context. By default it ignores the frame, line and master-clock columns, because another emulator will count time differently even when it executes the same instructions. Everything from the CPU column on must match: PC, opcode words, disassembly, register deltas and writes. Options relax the comparison further (--no-writes, --no-disasm) or include timing (--timing). A trace from another emulator has to be converted to this format first.

Tested against itself

The story asked for proof that trace-diff finds a divergence. CTest's cli.trace_golden does two things. It traces three frames of the synthetic boot ROM with --first and compares the result byte for byte with tests/golden/boot_trace.txt, so any change in CPU behaviour, timing or disassembly shows up. Then it copies the golden trace, changes one register delta, and requires trace-diff.py to report it. The second part runs when CMake finds Python 3.

The same writer is planned to back the debugger's trace from pause feature in M06, with a binary format and a ring buffer added there. The text format stays the reference.
