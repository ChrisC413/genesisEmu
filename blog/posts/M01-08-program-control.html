Branches, calls and knowing where you went

Control-flow instructions decide where the program goes next. The core also reports what kind of jump just happened, which the debugger and coverage tools rely on.

genesisEmu build notes5 min readStory M01-08

Everything that makes a program more than a straight list of instructions goes through a handful of opcodes: conditional branches (Bcc and BRA), subroutine calls (BSR and JSR), jumps (JMP), returns (RTS, RTR and RTE), and DBcc, the 68000's loop instruction. M01-08 implemented them and passed 100% of 72,585 vectors. It also added something the test suite doesn't check: an answer to "what kind of control transfer just happened?"

Branches are relative to the extension word

A branch carries a signed displacement: 8 bits packed into the opcode for the short form, or a 16-bit extension word for the long form. The base it's added to is the address just after the opcode, which is also the address of the word sitting in the prefetch register IRC. The opcode quirk in that comment is real. In the 68000's encoding, condition 0 is "always" (BRA) and condition 1 is "never". A branch that never branches is useless, so Motorola reused that encoding for BSR.

Timing differs for taken and not-taken branches. A taken branch costs 2 internal cycles plus refilling the prefetch queue at the target. A not-taken branch costs 4 internal cycles, plus skipping the extension word in the long form. The 16 condition codes come from a single function, testCondition, that mirrors table 3-19 of the Programmer's Reference Manual.

DBcc: a loop in one instruction

DBcc means "decrement and branch unless condition". It's the 68000's loop primitive: if the condition is true, fall through; otherwise decrement the low word of a data register and branch back unless it reached −1. The almost universal form is dbf d0,loop, where the condition is "false" and the instruction is a plain counted loop that runs D0+1 times.

Three timings exist: condition true (exit without decrementing), counter expired (exit after decrementing), and loop back. All three appear in the vectors.

The CPU already knows whether it just made a call, a return or a jump. The core reports it, so tools don't have to work it out again.

Odd targets and faulting jumps

A jump to an odd address can't fetch its first instruction, so the 68000 raises an address error. What gets stacked is not intuitive, and the suite pins it down. JSR has an ordering detail of its own. It fetches the first word at the target before pushing the return address. An odd target therefore faults with the stack untouched, and the story notes record it because a naive push-then-jump fails those vectors.

Returns

RTS pops the PC. RTR pops the condition codes (the low byte of SR) and then the PC. RTE, the return from an exception, pops the whole status register and then the PC, which can switch the CPU from supervisor back to user mode and swap stack pointers. On the original 68000 the exception frame is always this simple six-byte format (SR plus PC). Later 68k chips added format words; the story scopes RTE to the original 68000 frame.

Reporting the flow

The debugger's step over needs to know when an instruction was a call, so it can run until the matching return. A call-stack view needs calls and returns. Coverage maps want to tell branch targets from fall-through code. Working this out after the fact from the opcode bytes would duplicate decode logic and miss dynamic cases such as a not-taken branch, so the handler that already knows simply says so. A unit test steps through BSR, RTS and a NOP and checks Call, Return and Sequential in turn.

Verified

Bcc, BSR, DBcc, JMP, JSR, RTS, RTR, RTE and NOP pass 100% of 72,585 vectors, including odd-target address errors and exact cycle counts. JMP and JSR accept only the "control" addressing modes, which the decode table enforces at build time, so an invalid form such as jmp d0 falls through to the illegal-instruction handler as it should.
