Teaching the test suite to play Sonic

A small text format of "hold these buttons from frame N" lines, plus hash checkpoints, lets CI-style tests start a game, run right and jump, and prove the result is the same every time.

genesisEmu build notes4 min readStory M04-03

Until M04, every automated test of the real games ran with no input: boot, title screen, attract demo. That leaves out most of the game. To test actual gameplay automatically, the tests need to press buttons, the same buttons at the same frames every time. M04-03 added a minimal scripted-input format for exactly that.

It is deliberately not a movie or replay feature for users. Decision D-007 scopes the project's "freeze" features to pause, save states and trace-from-pause, and explicitly leaves input movies out. This format exists only for tests.

The format

A script is a text file of lines. An input line gives a frame, a port and the buttons to hold from that frame on. A checkpoint line names a frame and the kind of hash to check there. Here is the start of the Sonic 1 script in the repository:

The story added two things to the format spec 13 describes: an optional expected hash on each checkpoint line (so the script carries its own golden values) and the optional rom line, so a test can find the right dump in the user's ROM folder.

Semantics that keep it deterministic

An input line holds its buttons until the next line for the same port. Each line is latched at the start of its frame, which is the same once-per-frame latch from M04-01. A checkpoint at frame N is evaluated after N frames have run. The emulator is deterministic, so these rules fully define the run: the same script on the same ROM produces the same hashes.

The script holds only button presses and hashes. It contains nothing from the game, so it can live in a public repository.

Recording and checking

The CLI drives it:

  • gen_cli run --rom game.bin --input script.txt plays the script, runs at least to its last frame, and prints every checkpoint's hash.
  • --check turns mismatches, and checkpoints with no expected hash, into failures with exit code 3. A mismatching frame checkpoint also writes checkpoint_<N>.png into --out, so you can see what the game showed instead.
  • --update-script writes the computed hashes back into the script file, replacing old values and keeping comments. That's how a script is recorded in the first place.

Three scripts

The repository has one script per target game, each reaching the first act of play:

  • Sonic 1: start from the title, run right with jumps through the start of Green Hill Zone act 1. By frame 1,300 Sonic has run into a Motobug and been knocked back on the bridge, losing his rings, so collision and damage work.
  • Sonic 2: start at frame 950 (earlier presses during the title animation are ignored by the game), then run into Emerald Hill Zone act 1 with Tails following.
  • Sonic 3 & Knuckles: start, choose "no save" on the data-select screen, sit through the Angel Island intro, then run right and jump. Frame 2,400 shows Sonic in act 1 with a score of 100 and 7 rings.

The [rom] test Scripted input reaches the recorded checkpoints replays all three. The parser and the frame-accurate latching have their own unit tests that need no ROM: button lines and checkpoints parse, errors name the offending line, and the player latches buttons at exactly the frame they're scripted for.

Open: the second operating system

The acceptance criterion asks for the same frame hash every run on both operating systems. On Windows that holds: the hashes were recorded in one process and re-checked by the ROM test in another. A Mac hasn't run it yet, so the story says "Done on Windows; macOS run pending". When M05 added audio, the same scripts gained audio_hash checkpoints, and they became the regression net for sound too.
