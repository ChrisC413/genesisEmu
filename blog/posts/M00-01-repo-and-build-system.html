A build that works the same from every clean clone

Before a single opcode runs, an emulator needs a repository layout, a pinned toolchain and a hard line between the machine and the UI.

genesisEmu build notes5 min readStory M00-01

Most emulator write-ups start with the CPU. This one starts with the folder structure, because the folder structure decides what the emulator can become. genesisEmu is not only meant to play Sonic. It is meant to be a reverse-engineering workbench. It will trace every instruction, map which bytes of the ROM are code and which are data, and later rebuild the games from source. Each of those features needs to drive the emulated machine without a window in the way.

The first story, M00-01, therefore had a modest goal. Anyone should be able to build the project the same way from a clean clone, on Windows 11 or macOS, with one command.

Six modules, one direction of dependency

The architecture spec divides the code into libraries with a strict rule: dependencies only point downwards. At the bottom sits gen_core, the emulated hardware itself: CPUs, bus, video, audio, cartridge. It knows nothing about windows, files on disk, JSON or logging frameworks. Above it, gen_instrument adds tracing and coverage hooks, and gen_analysis builds the disassemblers on top of that. Two executables sit on top: the desktop app (genesisEmu) and a headless command-line runner (gen_cli).

The decision log records this as D-011: the core is a headless, deterministic library, separate from the UI. The reason is practical. CI can run thousands of CPU test vectors through it with no display attached. An analysis pass can replay a boot sequence and get the same answer every time. A future recompiler runtime could link against it.

One library appeared that the spec had not planned: gen_common. Both executables need configuration, logging and platform paths, but the core must stay free of them. The M00 pull request introduced gen_common as the shared home for those services and flagged it as a deviation to review.

The core knows nothing about windows, files, JSON or logging. That restriction is what makes it testable.

Presets instead of instructions

A README full of "run this, then pass that flag" drifts out of date. CMake presets put the instructions in the repository instead. CMakePresets.json defines a hidden base preset that wires in the vcpkg toolchain, then layers platform presets on top. A condition hides the Windows presets on macOS and the other way round:

The user-facing presets are win-debug, win-release, mac-debug, mac-release and a mac-asan build with AddressSanitizer and UndefinedBehaviorSanitizer. Building and testing on Windows is three commands, and the same three appear in the README.

The static x64-windows-static-md triplet was a deliberate deviation. The spec imagined a portable folder of "exe + DLLs". With static linking the portable build is just genesisEmu.exe and gen_cli.exe, and the licences of the linked libraries are installed under licenses/.

Pinning the third-party world

Dependencies come from vcpkg in manifest mode. The important line in vcpkg.json is the builtin-baseline, a vcpkg commit hash that fixes every library version. CI fetches exactly that vcpkg commit, so a library release upstream can't change the build without a commit in this repository.

The scope listed eight libraries. The pull request trimmed the list to what M00 actually used: SDL3, Dear ImGui with docking, spdlog, nlohmann-json and Catch2. SHA-1 and CRC32 were written in-house (about a hundred lines) instead of adding a hashing library. Others arrive with the milestone that needs them; by M05 the manifest also lists xxhash, and the YM2612 sound chip comes from the vendored, BSD-licensed ymfm library (D-013).

Warnings: strict in CI, forgiving at the desk

Every target goes through one small CMake function, so the warning level is the same everywhere:

Warnings are not errors in the presets. CI and the macOS validation script pass -DCMAKE_COMPILE_WARNING_AS_ERROR=ON instead. A stray unused variable won't block someone experimenting locally, but it won't get merged either. /external:W0 silences warnings from third-party headers, so the strict level only applies to the project's own code.

One later detail shows how the build changed as the code grew. The 68000 core uses a large decode table that instantiates many handler templates in a single file, which overflows MSVC's default object-file limits. src/core/CMakeLists.txt adds /bigobj to gen_core with a comment explaining why.

Licensing as a build input

The repository is public and MIT-licensed (D-014). The build treats that as a constraint as well as a file. Only permissively licensed sources may be consulted or vendored. THIRD_PARTY_NOTICES.md lists every component, and the install step copies the dependency copyright files next to the binaries. The .gitignore excludes ROMs and test data, so a careless git add can't commit a commercial game.

How it was verified, honestly

The acceptance criteria were small: both presets build, C++20 is on, warnings are strict, and a trivial Catch2 test runs through ctest. The story file records what was verified and what was not. The Windows build passed locally with Visual Studio 2022 and in CI, where windows-latest had already moved to Visual Studio 2026 (the presets don't pin a generator, so CMake picks up whichever is installed). The macOS box stayed unchecked, marked unverified: no Mac available, until it could be checked on real hardware. A later decision (D-025) raised the macOS minimum to 15.0 after libc++ version gates broke a Mac build in M03.

That honesty about unverified boxes runs through the whole project. A story is only "Done" when its criteria are met and its tests run in CI. That's why this foundational story still says "In progress".
